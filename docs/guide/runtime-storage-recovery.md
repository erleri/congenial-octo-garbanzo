# 집필 입력 저장·기술 보류 재개 정상화

상태: **PR #28 운영 반영·첫 실제 후속 실행 완료, 후속 후보 처리 오류는 로컬 수정 검증 중**. 시작 운영 버전은 `fe86f65`, 저장·재개 배포는 `af43672`이다. 앞선 [실제 실행 결과](report-followup-usage.md#후속-실행-종료와-남은-결함)의 세 결함을 함께 다룬다. 구현 존재·운영 배포·실제 생성은 각각 확인한다.

## 수정 범위

| 기존 결함 | 공통 경로의 변경 | 보존 경계 |
| --- | --- | --- |
| 과거 기술 보류가 완료한 케이스로 남음 | 승인된 worker가 기존 정책·입력을 유지한 채 제한된 기술 보류를 자동 재개. 원래 결과는 별도 불변 복구 이력에 남김 | 수동 케이스 초기화·원문 재작성·비용 초기화 없음 |
| 집필 task/context에 전체 이력이 반복돼 행 크기 제한 초과 | 기존 gzip 객체 저장을 집필 입력·요청 문맥에도 사용. 작은 명세서만 기존 행에 연결하고 읽을 때 정확한 순서·바이트·해시 복원 | 계산·모델 요청·원고·기존 /1 기록 유지, 행 한도 확대·이력 절단 없음 |
| 크기 오류가 출처 접근 문제로 분류됨 | runtime 저장 오류를 기술 장애로 우선 분류하고 관리자 운영 확인·Actions 실패 표시로 연결 | 내용 부족·기간 불일치·출처 이용 보류는 각자의 조건 유지 |

자동 복구 대상은 두 가지다. 첫째, `source_endpoint_preflight_hold`가 남아 있고 실제 요청 기록이 0건인 케이스다. 둘째, 집필 준비의 과거 크기 오류이며 해당 케이스의 기존 요청이 모두 비용 확인된 원문 처리인 경우다. 이미 집필한 케이스·미확정 비용·진행 중 요청·공개 원고는 이 복구로 초기화하지 않는다. 복구는 무료 plan에서 수행하지 않으며, 실제 execute의 기존 활성화·정책·예약·동시 실행 잠금 안에서 수행한다.

## 저장 구조와 권한

`runtime-document/2`는 원본 JSON을 Node gzip으로 압축해 기존 서버 전용 객체·조각 저장소에 보관한다. `runtime_documents`는 작은 조회·회계용 명세서와 객체 참조를 보관한다. 기존 SQL 원고 마감 함수에 필요한 packet은 같은 등록 기록에 native JSONB로 두며 문자열 사본을 더하지 않는다. 이 packet은 서버 전용이고 공개 원고의 승인·복사 조건을 바꾸지 않는다.

원본 상한 128MiB·압축 상한 32MiB·조각 512KiB·명세서 256KiB를 검사한다. 작은 기존 입력은 종전 inline 형식을 유지하며 큰 입력만 새 형식으로 보관한다. 기존 task·context 행 크기 제한은 유지한다. 객체 준비 → 조각 저장 → 완전성 확인 → 읽기 복원 → 명세 등록 → 실행 연결의 순서를 따른다. 누락·변조·불일치는 최신 자료로 대체하지 않는다.

새 테이블·등록·복구 함수는 service_role 전용이다. 익명·일반 로그인·관리자 브라우저에 원본 읽기 권한을 추가하지 않는다. 기존 작업의 회계·중복 방지·최종 마감 조건은 유지한다. 기존 공개 이력을 worker가 읽을 때 새 문맥도 복원하며, SQL 메일 조회에 필요한 통화·발행 사유는 작은 명세에 유지한다. 보관 객체의 자동 삭제는 도입하지 않는다.

## 실제 자료와 합성 검사의 구분

저장된 실제 COP 기사 검토 결과로 집필 준비를 무료 재생했다. 원래 1,612,274B task가 준비됐고 격리 DB의 운영용 RPC로 저장·조회해 같은 해시를 확인했다. 원문을 다시 모델에 보내거나 수동 원고를 만들지 않았다.

| 확인 | 로컬 결과 | 의미와 한계 |
| --- | --- | --- |
| 실제 COP task | 1,612,274B, 저장·복원 해시 동일 | 해당 저장 입력의 왕복이며 새 AI 원고 성공은 아님 |
| 실제 요청 문맥 | 2,431,647B → gzip 132,087B, 명세 1,482B | 코드·모델 요청을 바꾸지 않은 저장 표현 변경 |
| 저장/복원 시간 | 약 254ms / 43ms, 전체 검사 약 907ms | 로컬 실측. 운영 지연·성능 보장값 아님 |
| 마감·중복·검토 대기 | 실제 DB 함수 5항목 통과 후 롤백 | 합성 원고 저장 검사이며 실제 AI 생성·공개가 아님 |
| DB 전체 회귀 | PR #28 최종 CI 28파일·533항목 통과 | 기존 로컬 DB의 누적 시험 비용·보류는 유지하고 검사 전제만 분리 |
| 코드 전체 회귀 | PR #28 최종 CI 1,435항목 통과 | 검사 수를 원고 품질 표본으로 사용하지 않음 |

합성 검사는 이력 증가·압축 전후/명세서 한도·해제 출력 상한·조각 누락/변조/순서·저장 중단·재개·민감값·기술 오류 우선순위·무과금 plan의 무변경을 확인한다. DB 검사는 중복 복구 방지·원래 결과/비용/응답 보존·기존 집필 제외·미확정/진행 비용 차단·익명 권한 차단·장애 알림 중복과 해결을 확인한다.

## 운영 검증과 중단 기준

### 첫 실제 실행에서 확인한 결과

2026-11-10 22:43 KST에 저장·재개 코드 배포를 확인하고 생성 활성값을 복원했다. 무과금 [준비 점검 #3](https://github.com/erleri/congenial-octo-garbanzo/actions/runs/42827286279)은 원래 저장 입력으로 최대 $6.996155001·52회, 모델 호출 0회를 확인했다. 압축 전 50,770,620B·압축 후 8,976,778B·명세 1,254B이며 이미 보관된 객체를 재사용했다.

[실제 후속 실행 #4](https://github.com/erleri/congenial-octo-garbanzo/actions/runs/42828070743)는 최대 5회 중 첫 회다. worker가 과거 기술 보류 6건을 자동 재개했고 실제 모델 요청 11회·확정 비용 $0.2478475·새 미확정 비용 없음으로 종료했다. CLP는 11월 10일 원고를 집필·독립 검토해 `pending_review`로 저장했다. 이 원고의 집필·검토 비용은 $0.1389872이며 원문 처리 비용과 구분한다. 비공개 task 1개·context 2개가 새 보관 구조로 등록되어 실제 마감까지 연결됐다. 관리자 알림 작업도 성공했다. 기존 공개 원고 6건은 변경하지 않았다.

이 실행을 전체 정상 완료로 판정하지 않았다. COP에서는 처음부터 탈락한 후보 1건을 근거의 사후 철회처럼 취급해 다른 유효 근거 2건까지 막는 공통 경로 오류가 확인됐다. 또한 `partial_pending_review`와 적합 기사 없음의 정상 탐색 결과가 프로그램 수리 필요로 분류됐다. MXN의 기간·귀속 검토 탈락 및 BRL·PEN·ARS의 실제 자료 판본 변경은 이 오류들과 구분한다.

### 후속 수정의 범위와 검증

공통 후보 선택에서 **처음 탈락한 미사용 후보**와 **이미 채택한 근거의 철회·충돌·무효화**를 구분한다. 아직 task를 만들지 않았다면 탈락 후보는 일반 선택 단계에서 제외하고 다른 검증 자료를 평가한다. 이미 사용한 근거·과거 승인 근거·철회·충돌·재검토 필요 차단은 유지한다. 정상 탐색 상태는 진단에 남기되 기술 장애 알림으로 올리지 않고, 알 수 없는 오류는 계속 기술 장애로 다룬다.

`runtime-source-candidate/1` 복구는 해당 과거 사전 차단을 원래 입력으로 다시 검사하도록 worker에 한 번만 돌려준다. 이력·비용·응답을 보존하고, 집필 완료·진행 중/미확정 비용·철회·충돌은 복구 대상에서 제외한다. 재개 자체는 근거 승인이나 집필 자격이 아니다. 무료 plan은 조회만 하며 실제 execute에서만 복구한다.

저장된 실제 COP 입력 무료 재생에서 기존 차단 `original_pipeline_failed`가 없어졌고 승인 자료 2건·탈락 후보 1건 및 전체 입력 해시가 유지됐다. 새 모델 호출·운영 상태 수동 수정은 0건이다. 로컬 격리 DB는 후속 migration을 포함해 29파일·547항목을 통과했다. 이 후속 수정의 실제 운영 적용·다음 유료 실행 결과는 별도로 확정한다.

사용자 승인 범위는 같은 처리 조건에서 최대 5회 실제 실행·검증이며 문제 해결 시 조기 종료다. 각 실행은 최신 plan 상한과 **월 $30·실행 $7·요청 $0.25**를 확인한다. 재시도·백업·자동 공개·독자 메일 재발송을 추가하지 않는다. 이미 완료된 원문 단계는 기존 검토·요청·비용으로 재사용한다. 기사 내용·기간 부족을 통과시키기 위한 수동 카드·원고 교정은 하지 않는다.

운영 반영 전 CI와 추가 DB 변경을 확인하고, 생성만 전환 중 보류 → 진행 호출 확인·백업 → 추가 migration → 호환 코드 배포 → 무료 plan → report-only execute 순서로 진행한다. 케이스 재개는 worker의 새 공통 함수가 수행하며 운영자가 직접 상태를 바꾸지 않는다. 신규 결함이 발견되면 원인·비용·기존 기록을 남기고 수정·검증 뒤 다음 회차로 이어간다. 단순 대상 없음·자료 보류만으로 실제 생성 검증을 완료 처리하지 않는다.

완료는 발행 대상의 원문 처리·집필·독립 내용 검토·검토함 저장 및 필요한 관리자 알림이 자동 절차로 연결되고, 비용·재개·원본 보존과 신규 결함 여부를 실제 실행에서 확인한 상태다. 공개 여부는 기존 관리자 결정으로 남긴다.
