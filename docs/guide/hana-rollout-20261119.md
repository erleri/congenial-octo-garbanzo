# 하나은행 전환 운영 반영안

2026-11-18 로컬 구현·검증과 읽기 전용 운영 확인을 기준으로 작성했다. 적용 시작일은 **2026-11-19**다. 코드의 날짜와 설정값을 대조하며 시작일 전에는 기존 수집을 실행한다.

## 비교 기준 연결

누적 2%의 기준점은 최근 유효한 시장·정기 공개본의 날짜를 유지한다. 과거 원고의 원래 환율은 보존하고, 동일 날짜에 은행이 응답한 환율을 별도 비교 기록으로 저장한다. 은행 응답의 실제 날짜가 다르면 요청 날짜와 실제 날짜를 함께 남긴다. 누적 변동률은 현재 하나은행 값과 그 비교 기록 사이에서 계산한다. 기준점 교체를 새 발행으로 기록하거나 정기 일정을 미루지 않는다.

| --- | --- | --- | --- | --- |
| BRL | 2026-11-11 | 5.5539 | 5.583472920156337 | 2026-11-30 |
| MXN | 2026-11-02 | 18.8086 | 18.79699248120301 | 2026-11-16 |
| CLP | 2026-11-02 | 993.78040579 | 1000 | 2026-11-16 |

| PEN | 2026-11-02 | 3.4703247 | 3.45875 | 2026-11-16 |
| ARS | 2026-11-02 | 1532.39452727 | 1535.5 | 2026-11-16 |

표의 값은 11월 18일 읽기 전용 확인 시점의 자료다. 공개본이 추가·철회되면 해당 실행의 공개 이력에서 기준점을 다시 선택한다. 수집기는 공개본 관측일 목록을 끝까지 조회하고, 처음 필요한 날짜의 은행 값을 수집한다. 저장된 비교값은 재사용하며 다른 숫자로 갱신하지 않는다. 정기 예정일이 지난 통화는 기존 정기 원고 절차를 따른다.

대시보드 전일 대비와 리포트 숫자는 같은 비교 함수를 쓴다. 전환 첫날의 과거 화면 숫자와 은행 비교값은 구분한다. 새 원고에는 비교 기준 설명을 넣고 관리자 화면에도 누적 비교값을 표시한다. 새 하나은행 원고가 승인되면 이후에는 그 공개본의 하나은행 값을 직접 기준점으로 사용한다.

## 운영 적용 순서

1. PR의 코드·문서·전체 회귀·DB CI 결과와 main의 최신 자료일을 확인한다. 11월 19일 이후 기존 출처 확정값이 이미 있으면 시작일을 다음 미채택 날짜로 다시 준비하고 검증한다.
2. 기존 생성 활성값·비용 예약·진행 중 호출을 확인하고, 운영 환율 전체 이력과 공개 원고의 복구 기준점을 보관한다.
3. 검증 커밋을 main에 병합하여 Netlify 코드 배포를 확인한다. DB migration은 이번 변경에 없다.
4. GitHub Actions 변수 `FX_HANA_EFFECTIVE_FROM`을 `2026-11-19`로 설정한다. 기존 Supabase URL·서버 키를 생성 작업에도 전달해 공개된 리포트의 관측일만 조회한다. 설정을 앞서 등록해도 시작일 전에는 수집 기준을 바꾸지 않는다.
5. 첫 수집 실행에서 최초 고시 1회차·고시일시, PEN·ARS 실제 기준일, 원본값·역산·출처 기록, 전체 이력 보존, DB 숫자와 파일 버전의 일치를 확인한다. 리포트 전용 점검으로 당일 전일 대비와 6통화 누적 기준·정기 예정일을 확인한다.
6. 실제 생성 호출은 그 시점의 예산·비용 복구 조건 안에서만 진행한다. 현재 별도로 남은 BRL 502 비용 미확정 문제가 유료 처리를 차단할 수 있다.

자동 환율 갱신은 `public/fx-reference-context.json`을 숫자 파일과 같은 커밋으로 전달한다. DB 조회 화면은 이 작은 비교·출처 문서의 버전을 확인하고 연결한다. DB와 파일 버전이 다르면 기존 저장 화면으로 대기하고 다음 새로고침에서 재확인한다. 전체 환율 이력은 이 문서에 복제하지 않는다.

## 실패·복구

은행 날짜·회차·통화·표 구조·값이 맞지 않으면 새 파일 기록 전에 오류를 반환한다. 직전 운영 자료는 보존된다. 조회한 과거 날짜의 비교 기록이 누락되거나 변조되면 해당 비교를 기술 보류로 표시하며 다른 공급자 값으로 대신 계산하지 않는다. 이미 사용한 은행 비교 기록과 원고·비용 예약은 삭제하지 않는다.

시작 후에는 저장된 적용일을 다음 실행에서도 사용한다. 변수 누락만으로 기존 출처로 되돌아가지 않는다. 복구 시에는 새 자료 갱신·새 유료 처리를 보류하고 마지막 확인 자료를 유지한 상태에서 수집 또는 코드 문제를 수정한다. 과거 숫자의 덮어쓰기나 비교 기록 삭제로 차단을 해제하지 않는다.
