# 앱 설계도 작업 인계

> 후속 완료: [FigJam 실제 지도](figjam-app-map-review-20261030.md)가 작성됐고, [발행 정책 재확인/상태표](pre-ui-policy-review-20261030.md)를 추가했다. 아래 외부 파일 미생성 문구는 최초 인계 당시 기록이다.

2026-10-30 · 운영 데이터 계획6단계 다음 작업 · 아직 Figma/FigJam 변경 없음

## 목적과 작업 순서

사용자가 전체 구조를 보고 말로 수정 방향을 결정할 수 있게 한다. **전체를 한 장으로 보고 리포트 흐름만 펼쳐 보기**부터 이어간다. 리포트 기능 추가나 UI2.0 구현을 먼저 진행하지 않는다. 설계도 확정이 전체 출시 승인은 아니다.

기존 대화 **「앱 설계도 볼 로우코드 플랫폼 찾기」**(01a18841-5d5b-7c61-a03e-5ad63a800483)의 초안을 재사용한다. 그 대화에서는 로컬 시각화 지도와 단계 번호를 만들었다. Figma/FigJam 파일을 완성한 기록은 확인하지 않았다. 다음 작업에서는 사용자가 요청한 Figma/FigJam 설계도 정리·검토를 이 초안에서 이어간다. 실제 외부 파일 생성과 화면 확인이 끝나기 전에 Figma 완료라고 보고하지 않는다. 이번 인계만으로 다른 대화에 후속 메시지를 보내거나 파일을 편집하지 않는다.

## 지도에 반드시 구분해 표시할 것

| 구분 | 담을 내용 |
| --- | --- |
| 운영 중 | 기존 환율 API→생성/동기화→DB/JSON→대시보드/월별/일별/계획환율, 기존 이메일, legacy 리포트 경로 |
| 로컬 구현·검증 | 공통6통화 자료/카드/집필 입력, Sol 기본·명시적 모델 교체, A안, 별도 DB 승인/공개 조회, 파일 장부·암호화 복원 |
| 운영 연결 미완료 | 새 Sol 집필의 정기 실행, 영속 비공개 파일/비용 장부, 운영 provider/중지 계약, 추가 DB 구조7개 |
| 사용자 결정/후속 | UI2.0 메뉴/통합, 실제 달력/이력 연결, 실제 품질/파일럿, 독립 백업·키 책임·월 한도와 최종 공개 승인 |

720개 다른 경로를 지도 상자로 늘어놓지 않는다. 사용자 기능과 업무 흐름을 먼저 보여 주고 선택한 단계에서만 코드/근거 문서로 연결한다.

## 리포트 상세에서 보여 줄 흐름

1. **쓸 만한 변화가 있는가:** 대시보드와 같은 기준환율로 마지막 유효 발행본 대비 누적 변화·정기 점검·새 사건·정정을 판단한다. 6개 통화 모두 누적±2%와 유효 발행 후14일이 지난 첫 한국 월요일 점검으로 확정됐다. PEN/ARS 미결정 표시는 10월30일 재검토에서 정정했다. 계기는 발행 승인이 아니다.
2. **무슨 자료가 필요한가:** 질문 계획→국가별 무료 뉴스/공식 API 선택→조회→시점/기간/가격 종류/이용 범위→사실·귀속 견해 카드. 기사 가격은 대표환율을 대체하지 않는다. 소비 통계와 당일 원인을 구분한다.
3. **AI에게 보낼 입력 준비:** 같은 기준환율 스냅샷·차트·승인된 카드·원리·중복 정리·공통 지침·주장-근거 대응. 부족/실패/보류를 구분한다.
4. **원고 작성:** 서버에서 GPT Sol 기본. 제공 경로·가격/조건·예산·중복을 확인하고 승인 범위에서만 호출한다. 새로고침/화면 열기로 호출하지 않는다. 클로드/제미나이는 명시적으로 교체할 수 있게 두되 자동 전환하지 않는다.
5. **검사와 검토:** 구조/수치/ID 검사와 실제 문장 지지·기간/귀속/설명 범위 검토를 분리. 출처 ID만 붙이면 의미 검토가 끝나는 구조로 그리지 않는다.
6. **승인과 읽기:** 저장 완료·근거 판본 확인→active admin 승인/반려→정제 공개본→목록/상세/근거·이력. 초안은 대체 공개하지 않는다.
7. **장애·정정·운영:** 실패/비용 미확인→새 호출 보류, 기존 환율·메일 유지. 철회 캐시·재검토·비공개 보존/복원·API 상태 확인을 관련 단계에 연결한다.

이 번호는 설명용 순서다. 기존 지도 자체의 D/R3 등 식별자는 확인 없이 재배정하지 않는다. 실제 초안을 읽고 사용자가 이미 익힌 번호와 대응시킨다.

## 사용자와 먼저 볼 질문

- 전체 지도에서 ‘환율 보기’, ‘계획값 관리’, ‘리포트 만들기/읽기’, ‘운영 관리’가 구분되는가?
- 리포트가 보류되는 곳과 사람이 판단하는 곳이 눈에 보이는가?
- ‘계획 대비+관리’ 통합 같은 메뉴 제안은 어떤 사용자 목적을 돕는가? 통합으로 공개 조회와 관리자 쓰기 권한을 섞지는 않는가?

첫 검토에서 모든 화면을 새로 디자인하지 않는다. 구조/상태/번호를 먼저 맞춘 뒤 리포트 기능 확인과 UI2.0을 진행한다.

## 코드와의 연결 근거

- 현재 운영/로컬 기준: [운영 전환 준비](rollout-preparation-20261030.md).
- 현재 사용자 화면·진입 분기: `src/App.tsx`.
- 기존 데이터/계획값: `src/hooks/useExchangeData.ts`, `src/lib/exchangeRateRepository.ts`, `src/lib/businessPlanRemote.ts`.
- 로컬 A안/승인/조회: `src/components/PublishedCurrencyReports.tsx`, `src/local-report/provider.ts`, `src/local-report/DbReview.tsx`.
- 공통 입력과 자료 준비: `scripts/currency-report/shared-writer.js`, `report-preparation.js`, `publication-cadence.js`.
- 저장/보존/복원: `scripts/currency-report/data-ledger.js`, `recovery.js`, [복구 절차](recovery-runbook.md).
- 기존 자동 작업: `.github/workflows/generate-data.yml`. 새 집필 경로의 운영 자동화로 표시하지 않는다.

설계도에 키·토큰·수신자·계정·비공개 원문·원문 응답을 넣지 않는다. 상태/기능 이름·공개 자료 경로·필요한 코드 위치만 사용한다. 설계도와 코드의 자동 양방향 동기화는 구현하지 않았으므로, 변경할 때 연결 문서·기준 커밋·상태를 함께 갱신한다.
