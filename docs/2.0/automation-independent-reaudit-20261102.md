# 6통화 자동 처리 독립 재점검 — 2026-11-02

## 판정

**자동 재개는 아직 불합격이다. 신규 유료 전체 시험보다 공통 작업 식별·대체 처리를 먼저 수정한다.**

앞선 A1~A5 수정에서 고정 입력 재개, 충돌 근거 격리, 오류 전달, 장부 보존은 개선됐다. 그러나 입력 갱신과 재개를 결합하면 두 가지 막힘이 남는다. 특정 국가 규칙 문제가 아니라 BRL·MXN·COP·PEN·CLP·ARS 모두에 적용되는 공통 경로 문제다.

이번 작업은 코드 읽기, 새 장애 재현, 기존 관련 검사, 실제 저장 응답 재생, 격리 DB의 롤백 검사다. 구현 코드·기존 원고·환율·비용 기록은 고치지 않았다. 새 외부 조회·모델 호출·지출·운영 변경은 없다. 별도 모델이나 다른 에이전트의 검토를 사용하지 않았다. 앞선 완료 주장과 분리한 조건으로 같은 에이전트가 재점검했다.

## R1 · 해당 통화 기준환율 갱신 후 집필 작업 번호 충돌 — 높음

- 위치: `scripts/currency-report/runtime.js:77,174`, `scripts/currency-report/operating-cycle.js:154`.
- 재현: 첫 집필 성공 → 원고 검토 전 일시 장애 → 해당 통화의 저장 기준환율 변경 → 다음 실행.
- 관찰: 사건 키는 새 기준환율을 반영하지만 집필 `taskKey`는 이전 것과 같다. 집필 입력의 가격은 바뀌었으므로 요청 해시가 다르다. 기존 응답 재사용 검사에서 `existing_runtime_call_hold`로 멈추고, 다음 실행도 완료된 배치의 같은 보류를 반환한다.
- 범위: 6통화 각각 재현했다. 원래 작성 응답·비용은 보존되고 새 호출은 0이지만 검토 초안은 5개에 머문다. 1%의 가상 수정은 재현용 값이며 발행 임계값 제안이 아니다.
- 원인: 발행 사건, 사건의 입력 판본, 유료 요청의 식별이 일관되지 않다. 사건은 같아도 가격 판본은 달라질 수 있다.
- 수정 방향: 같은 입력의 재개와 검증된 새 입력 판본을 구분해 사건→입력 판본→단계 요청의 연결을 고정한다. 새 난수/날짜로 중복 제한을 피하면 안 된다. 예산·이미 게시/검토 대기 중인 원고·옛 미완료 단계·수정 사유를 함께 확인하고, 승인 범위 밖의 새 비용은 명시적으로 대기시킨다.

## R2 · 다른 통화 갱신이 대기 중인 통화를 고립시킴 — 높음

- 위치: `scripts/currency-report/operating-cycle.js:78-89`, `supabase/migrations/20261101163805_currency_operating_zero_dispatch_continuation.sql:106-114`.
- 재현: COP 원고 작성 완료·검토 대기 → BRL 기준환율만 변경 → 다음 실행. 나머지 통화를 대기 대상으로 바꾸어도 같다.
- 관찰: 전체 6통화 reference 해시가 달라져 기존 배치를 종료하고 모든 대기 사건을 held로 바꾼다. COP 자신의 가격·자료는 같아 사건 키도 같다. 새 배치에서 그 키를 다시 요구하면 DB가 `unchanged_case_already_processed`를 반환한다. 이후 실행도 진행되지 않는다.
- 실제 DB 확인: 설치된 격리 DB 함수에서도 명시적 종료 이후 같은 사건 키를 새 배치에서 재개할 수 없음을 확인했다. 시험 기록은 모두 롤백했다.
- 추가 영향: 이 누락은 자료 변화 대기로 분류되고, 다른 5개 원고가 검토 대기이면 전체 상태는 `review_wait`, 종료 코드는 0이다. 기술적으로 고립된 작업이라는 경보가 사라진다.
- 수정 방향: 영향 판단을 대기 통화의 입력과 실제 공통 의존 자료 기준으로 한다. 다른 통화만 바뀌었다면 원래 입력·사건·장부를 유지해 검토를 끝내고 새 자료는 후속 실행으로 넘긴다. 배치를 바꿔야 할 때는 국가별 미완료 작업의 인계/종료를 명시하고, 단순 중복으로 숨기지 않는다. 공통 예산과 동시에 실행되는 작업의 잠금은 그대로 유지한다.

## R3 · 저장된 결과의 마무리가 외부 모델 목록에 의존 — 중간

- 위치: `scripts/currency-report/runtime.js:165-171`.
- 재현: 집필·검토와 DB 저장은 성공했으나 저장 확인 응답 유실 → 다음 실행에서 모델 제공 경로 조회 장애.
- 관찰: 저장된 작업 조회보다 외부 사전 점검이 먼저 실행된다. 모델 호출이 필요 없는 상황에서도 `runtime_endpoint_preflight_wait`로 멈춘다. 합성 원고 6개는 이미 저장돼 있고 추가 호출은 0이다.
- 수정 방향: 현재 실행 권한·요청 해시·검토 버전·확정 비용·응답의 모델 신원을 먼저 검사해 동일 저장 응답인지 판단한다. 외부 제공 경로 점검은 실제 새 전송 직전에만 필요하다. 이미 저장된 결과에 대한 무조건 신뢰나 권한 우회로 바꾸지 않는다.

## 확인된 개선과 검증 공백

| 구분 | 이번 결과 |
|---|---|
| 동일 입력에서 검토만 재개 | 기존 6통화 회귀 검사 통과 |
| 동일 원고 저장의 확인 응답 유실 | 기존 메모리/DB 검사 통과. 외부 목록 장애가 겹치면 R3 |
| 다른 국가 새 기사·한국 날짜 변경 | 기존 검사 통과. 다른 국가 **가격 변경**은 R2 |
| 기준환율 변경 | 추출/대조 대기 단계의 기존 검사는 통과. **집필 완료 후**는 R1 |
| 성공·반려 충돌, 해결된 반려, 오류 재조회 | 관련 기존 검사 통과 |
| 실제 과거 요청/원고/비용 보존 | v3 요청 21개 동일 재현, 입력 파일 4개 해시 일치 |
| 알려진 MXN 옛 잘못된 성공 판정 | 현재 자동 재사용 보류 확인. 새 모델이 모순을 잡는지는 미시험 |
| 경제적 설명 품질 | 새 실제 원고를 만들지 않았으므로 이번 합격 대상 아님 |

관련 기존 자동 검사 34개는 모두 통과했다. 추가한 **12가지 국가·가격 변경 조합은 결함 재현**이며 통과한 제품 기능으로 세지 않는다. 저장 확인 응답 유실+외부 목록 장애 1건도 추가 재현했다. DB 기존 23검사를 다시 실행했고, 별도 실행에서는 그 검사에 현상 확인 1개를 추가했다. TAP의 추가 `ok`는 잘못된 동작이 예상대로 관찰됐다는 뜻이지 기능 합격이 아니다.

전체 빌드·전체 회귀는 이번에 다시 하지 않았다. 제품 코드를 수정하지 않았으며 관련 경로만 재검증했다. 실제 Supabase HTTP 어댑터와 6통화 모델을 함께 실행하는 전체 시험은 수행하지 않았다. Node 재현은 합성 store/transport이고 SQL 관찰은 설치된 격리 DB 함수다. 두 범위를 혼동하지 않는다.
