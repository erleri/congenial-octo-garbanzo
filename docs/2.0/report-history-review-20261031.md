# 리포트 조회·표시 규칙 최종 검토

2026-10-31 KST · 문서 검토 완료 · 구현 전

## 결론과 적용 범위

기존 계획의 방향은 유지한다. **6통화 최신 카드 → 통화별 지난 리포트 → 기존 A안 상세**로 구현을 진행할 수 있다. 다만 최근30개에 종속된 상세 조회, 공개 판본 교체, 철회와 조회 실패의 혼동은 아래 기준으로 먼저 해결한다. 목록만 늘려 완료 처리하지 않는다.

이 문서는 [이력 작업 계획](report-history-work-plan-20261031.md)의 미정 사항을 보완한 구현 기준이다. [상태·행동표](report-state-actions-20261030.md)의 조사 상태/게시 상태/조회 상태 분리는 유지한다. 새 조사 상태 공개, 발행 정책 변경, 집필, 관리자 전체 재설계는 이번 범위에 추가하지 않는다.

이번 검토는 저장 코드·migration·기존 문서를 대조한 결과다. DB 실행 검증이나 브라우저 동작 시험을 새로 수행한 결과가 아니다. 원고·환율·앱 코드·DB·운영은 변경하지 않는다.

## 1. 최신·이력·유형의 의미

- 최신은 **통화별 현재 유효한 실제 공개본 중 기준일이 가장 최근인 것**이다. 공개시각이 늦다는 이유로 과거 날짜를 최신으로 올리지 않는다. 기준일·실제 관측일·공개/정정시각은 각각 유지한다.
- 역사 사례(`historicalReview`)는 최신 추천에서 제외하되 공개 승인된 경우 이력에서 ‘과거 사례’로 찾아 읽는다. 실제 최신이 없으면 ‘현재 리포트 미발행’과 ‘과거 사례 보기’를 함께 제공한다. 기존 칠레 과거 원고를 숨기거나 현재 원고로 바꾸지 않는다.
- 합성(`testOnly`)은 실제 공개 조회에서 제외한다. 로컬 검증 모드에만 명시적으로 포함하고 ‘합성 연결 시험’ 표시를 유지한다. 실제 원고가 없다는 이유로 자동 대체하지 않는다.
- 최신 카드/대시보드/통화 최신 주소는 같은 선택 규칙을 사용한다. 이전 본문을 유지할 때도 원래 기준일을 표시한다. 신규 조사 실패가 기존 정상본의 날짜나 상태를 바꾸지 않는다.
- **분석 목적**(환율 설명/경제 환경)과 **발행 계기**(변동 분석/정기 점검)는 별도 값이다. 정기 점검은 경제 환경만 다룰 수도 있다. 제목이나 `purpose`로 발행 계기를 추측하지 않는다. 확인되지 않은 과거 자료의 유형은 ‘리포트’다.
- 현 저장 구조에 맞춰 한 통화·기준일에는 유효 공개본 하나를 유지한다. 같은 날짜에 다른 목적의 원고가 생겨도 자동 덮어쓰지 않는다. 교체 대상/유형을 확인한 승인만 허용한다. 같은 날 독립된 여러 공개 리포트를 발행하는 기능은 이번 범위 밖이다.
- 신규 배지는 검증된 실제 공개 당일(KST)에만 표시한다. 정정/편집 교체는 신규 발행으로 세지 않는다. 정정 표시는 해당 판본의 이력 정보이며 일일 새 배지와 다르다. 발행 기준점과 2주 점검 시계도 정정 때문에 초기화하지 않는다.

## 2. 주소와 이동 규칙

| 주소/행동 | 결과 |
|---|---|
| `#report` | 6통화 최신 요약. 본문·전체 과거 목록을 미리 받지 않음 |
| `#report/CLP` | CLP 최신 유효 실제본. 없으면 미발행과 과거 사례 진입 안내 |
| `#report/CLP/history?year=2026&month=10` | 제안했던 이력 주소를 이 형식으로 고정. 연도·월 생략은 전체, 월만 지정은 주소 오류 |
| `#report/CLP/2026-10-09` | 해당 기준일의 현재 유효본 정확 조회. 정정됐다면 안내 포함 |
| 기존 `?run=공개ID#report/CLP/2026-10-09` | ID·통화·날짜 일치 확인. 교체/철회 시 본문 대신 상태. 다른 원고 자동 대체 금지 |
| 이전/다음 | 같은 통화·현재 기간 조건 안의 더 오래된/더 최근인 유효 기준일. 버튼에 방향과 날짜 표시 |
| 최신본 보기 | 기간 조건을 벗어나 통화 최신으로 이동한다고 명시 |
| 목록으로/원래 화면으로 | 목록의 기간·불러온 범위·가능한 스크롤 복원. 추이 복귀는 별도 버튼으로 기존 맥락 유지 |

달력에 없는 날짜, 알 수 없는 통화, 잘못된 연도/월, 빈/복수 run은 정상 주소로 보정해 다른 글을 열지 않는다. 목록 진입에는 `run`을 제거한다. 복사 링크는 보고서 식별 주소이며 임의의 외부 복귀 URL은 받아들이지 않는다. 기간 맥락이 없는 직접 링크의 이전/다음은 전체 이력 기준이다.

새로고침/뒤로가기에는 검증된 내부 상태를 복원한다. 저장 공간 제한 등으로 전체 스크롤 복원이 불가능하면 같은 기간 목록을 다시 조회하고 안내한다. 본문 링크가 살아 있다는 이유로 목록 페이지 캐시도 영구 보존하지 않는다.

## 3. 필요한 공개 조회와 응답

아래는 구현해야 할 동작 정의이며 아직 API가 추가된 것은 아니다.

| 조회 | 최소 결과 | 실패 격리 |
|---|---|---|
| 최신 요약 | 통화별 유효 요약 또는 성공한 빈 결과 | 한 통화 실패를 다른5통화 미발행으로 만들지 않음 |
| 기간 목록 | 최대30개 요약 + 다음 cursor/hasMore | 서버에서 기간 적용 후 페이지 제한. 오류를 더 없음으로 바꾸지 않음 |
| 발행 기간 | 공개 이력에 실제 존재하는 연도/월 | 이 정보 실패가 직접 날짜 상세를 막지 않음 |
| 정확 상세 | 지정 ID/날짜의 공개 상태와 허용된 본문 | 최근 목록을 먼저 가져올 필요 없음 |
| 이전/다음 | 동일 조건에서 이웃 요약 각각 최대1개 | 실패 시 본문은 유지하고 탐색만 재시도 가능 |

- 요약 허용값: 공개 ID·통화·기준일·실제 관측일·제목·짧은 요약·생성 방식·확인된 유형·역사/시험 구분·공개/정정시각. 본문·비공개 검토/원문/비용은 목록에 포함하지 않는다.
- 게시 상태: 유효/교체/철회. 조회 결과: 성공/없음/실패. 캐시 사용 여부와 상태 확인시각은 별도다. 한 문자열 `passed`로 합치지 않는다.
- `not_found`는 성공한 정확 조회에서만 반환한다. 미발행은 성공한 최신 조회에 유효본이 없는 경우다. 실패한 조회나 일부 실패한 목록에서 ‘없음’을 추론하지 않는다.
- 커서는 마지막 기준일과 통화·기간·자료 범위에 결합한다. 다른 통화/필터의 커서 재사용은 거부한다. 엄격한 DB 스냅샷은 약속하지 않는다. 중간 정정/발행은 중복 제거·변경 안내 후 최신 조회로 반영한다.
- 동일 공개 ID에 다른 본문이 들어오면 정상 갱신으로 보지 않는다. 수정은 새 ID로 승인한다. 같은 날짜 여러 행 문제를 클라이언트 ID 문자열 정렬로 해결하지 않는다.

## 4. 정정·철회 저장 방향

**기존 공개표를 현재 유효 본문의 저장소로 유지하고, 공개됐던 ID의 상태·교체 관계만 별도의 작은 공개 기록으로 보강**하는 방향으로 구현한다. 모든 예전 본문을 공개 저장하는 아카이브를 새로 만들지 않는다. 비공개 원고/검토 원본 보존은 기존 구조를 유지한다.

공개 기록에는 공개 ID·통화·기준일·확인된 공개시각·상태 변경시각·상태 순서값·교체 유형·현재 유효 수정본 연결만 둔다. 과거 본문/요약/차트, 검토자, 내부 오류, 관리자 자유 입력 반려/철회 이유는 복사하지 않는다. 독자 안내는 정해진 상태 문구로 만든다.

- 승인/교체/철회와 공개 상태 기록을 같은 트랜잭션으로 갱신한다. DB의 기존 통화·날짜 잠금과 active admin 재확인을 재사용한다. 동시 교체에서 뒤늦게 승인한 사람이 모르는 새 판본을 덮어쓰지 않게 현재 공개 ID 비교를 추가한다.
- 과거 ID → 수정본 → 다시 수정본은 유효한 최종 연결로 안내한다. 최종본도 철회됐다면 ‘유효 수정본 없음’이다. 다른 날짜의 보고서는 별도 대안 링크이며 수정본으로 부르지 않는다. 순환/다른 통화·날짜 연결은 거부한다.
- 미승인 초안 ID는 공개 상태 조회에서도 `not_found`다. 공개됐다는 확인 없이 private runs 전체를 공개 기록으로 이관하지 않는다. 과거 공개/정정 시각이 불명확하면 미확인으로 남긴다.
- 현재 `report.id`의 누락/중복/통화·날짜 충돌을 먼저 읽기 검사한다. 문제가 있으면 해당 자료의 이관을 보류하고 이유를 남긴다. 옛 링크를 바꾸거나 임의 ID를 붙여 원고를 덮어쓰지 않는다.
- 일반 독자의 쓰기 권한은 추가하지 않는다. 새 공개 기록도 필요한 안전한 읽기만 허용한다. 실제 보안·원자성 검증 전에는 구현 완료라고 하지 않는다.
- 철회로 최신본이 없어지면 영향을 받지 않은 더 과거 유효본을 새 날짜처럼 바꾸지 않고 제시한다. 오류가 여러 원고에 걸친 경우 해당 ID들을 함께 차단해야 하며, 과거 원고라는 이유만으로 안전하다고 간주하지 않는다.

## 5. 캐시와 장애

| 상황 | 화면/캐시 처리 |
|---|---|
| 철회·교체를 확인 | 그 ID의 본문/요약/차트를 화면과 모든 목록·상세 캐시에서 제거. 늦은 성공 응답으로 부활 금지 |
| 성공한 정확 조회에서 없음 | 해당 캐시 무효화. 영구 철회 표식을 만들지 않으며 이후 명시적 재조회 허용 |
| 서버/연결 실패 + 사용 가능한 공개 캐시 | 캐시·원래 기준일·마지막 게시 상태 확인시각·현재 상태 미확인 표시 |
| 서버/연결 실패 + 캐시 없음/만료 | 불러오기 실패와 다시 시도. 미발행/변화 없음으로 바꾸지 않음 |
| 상태는 철회인데 본문 서버는 옛 성공 응답 | 상태 순서값과 알려진 ID 차단이 우선 |
| 캐시 저장소 사용 불가/용량 초과 | 읽기는 계속, 선택적 캐시만 포기. 실패를 DB 오류로 확대하지 않음 |

목록·본문의 확인시각을 섞지 않는다. 목록 성공만으로 본문의 게시 상태를 새로 확인했다고 기록하지 않는다. 상세 진입/창 복귀/기존 주기 재확인 시 상태를 확인하되 화면 조회가 AI를 호출하지 않는다.

로컬 검증 상한은 **본문10건, 목록 페이지12개, 합계 UTF-8 JSON 5MiB**, 초과 시 최근 미사용 항목부터 제거하는 기본안으로 둔다. 개별 항목이 상한보다 크면 캐시하지 않고 읽기만 허용한다. 기존24시간 만료·15분 상태 확인은 그대로 로컬 시험값이다. 차단 상태는 본문 캐시 퇴출로 지우지 않는다. 클라이언트가 모르는 철회의 완전 오프라인 즉시 반영은 보장하지 않는다. 운영 상한/철회 전파 지연 승인은 출시 전에 별도로 남긴다.

30개는 한 번에 조회할 수량이다. DB 원고 삭제, 보존 기간 실행, 서버 감사 기록 삭제와 관계없다.

## 6. 구현 합격 판정

| 검증 묶음 | 핵심 합격 조건 |
|---|---|
| 과거 탐색 | 합성65기준일의30+30+5, 연도/월 경계, 첫30밖 직접 주소. 실제 원고와 합성 표본 분리 |
| 선택·맥락 | 역사/합성 최신 제외, 잘못된 날짜/run 대체 없음, 기간 안 이웃·기간 밖 최신, 뒤로가기/새로고침 |
| 판본·권한 | 같은 날짜 동시 교체 충돌, 정정 연결·최종 철회, 초안 ID 비노출, anon 쓰기 차단, active admin 재확인 |
| 장애·캐시 | 미존재 후 새 발행 조회 가능, 알려진 철회 후 늦은 응답 차단, 목록 실패에도 직접 상세 가능, 국가별 부분 실패, 캐시 총량/만료/저장 불가 |
| 기존 서비스 | A안 본문/수치/날짜·대시보드·추이 복귀·새 배지 보존, 원래 원고/감사 이력 보존 |

이 묶음에 필요한 기존 테스트를 먼저 재사용한다. 같은 조건을 여러 파일에서 중복해 개수만 늘리지 않는다. 새로운 DB 경로는 격리 DB pgTAP/실제 조회, 화면은 PC·390px, 코드 변경 후 타입·린트·전체 회귀·관련 빌드로 검증한다. 이번 문서 검토에서는 이 구현 시험을 아직 실행하지 않았다.

## 다음 작업과 남겨둔 결정

**다음은 Sol High로 로컬 구현을 연속 진행한다:** 저장 자료 ID 점검 → 공개 상태·정확 조회·기간 조회 → 이력 화면 → 정정/장애·캐시 → 묶음 검증. 이 검토를 다시 하기 위해 국가별 뉴스나 집필 모델 선택으로 돌아가지 않는다.

구현에 필요한 조회·표시 기준은 위와 같이 고정했다. 출시 전 별도 결정은 운영 캐시/확인 주기, 운영 DB 이관·배포, 전체2.0 출시 승인이다. 이번에는 새 유료 호출·운영 변경·공개 원고 편집을 하지 않는다.
