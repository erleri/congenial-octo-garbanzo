# 저장 오류·집필 근거 범위 공통 수정 — 2026-11-02

## 결과

[독립 점검 V1·V2](final-validity-independent-audit-20261102.md)의 두 재현 경로를 수정했다. 전체 **168파일·1,240검사**, 타입 검사, 전체 린트, 마지막 변경 파일 린트, 운영/앱 리포트/리포트 전용 빌드와 번들 경계 검사가 통과했다. 실제 저장 어댑터·격리 SQL에서도 원래 일회 승인 범위 안의 복구를 확인했다.

이 결과는 두 코드 결함과 관련 회귀의 검증이다. 새 실제 모델 원고의 품질·제공자 HTTP 연결·게시·출시 합격을 뜻하지 않는다. 이번 실제 모델/뉴스 호출·신규 비용·운영 변경은 0이다. 공개 기술 문서만 읽었다.

## V1 — 무결성 오류를 복구 필요로 전달

`runtime-store.js`에서 실제 RPC 오류의 성격을 보존한다. 확인된 연결/풀 시간 초과 등 가용성 오류만 일시적인 읽기 대기로 인정한다. DB 권한·스키마 오류, 알 수 없는 오류, 원본 보존 필드 누락, 원본 JSON 해석 실패, 저장된 표현 불일치는 일반 조회 대기로 바꾸지 않는다.

- 임시 대기 판정은 실제 저장 어댑터가 만든 오류이며, 근거 캐시/집필 입력의 두 읽기 작업에서 발생한 경우에만 적용한다.
- 일반 오류 메시지에 `runtime_store_..._failed`를 붙였다는 이유만으로 임시 대기를 허용하지 않는다.
- 저장 서비스의 원시 오류 메시지·상세·스택을 실행 기록에 복사하지 않는다. 실행에는 안전한 작업/오류 이유를 남긴다.
- 복원할 JSON 자체가 깨진 경우도 `runtime_exact_json_invalid`라는 일정한 이유를 남긴다.
- 처리할 수 없는 실행 예외는 `operating_execution_hold`와 구체적 이유/보류 목록으로 반환한다. 다른 국가가 승인 대기여도 전체 결과는 복구 필요(`action_required`, 종료 코드 2)다.
- 자동 재시도는 추가하지 않았다. 원래 입력·작성 응답·장부를 보존하며 복구 후 남은 단계만 재개한다.

6통화 각각에서 표현 불일치·원본 필드 누락·깨진 JSON을 두 번 연속 입력해 추가 호출 0과 복구 경고를 확인했다. 복구 후에는 원래 검토 1회만 진행했다. 권한/스키마/미분류 예외·근거 캐시 복원 오류도 별도로 확인했다. 정상 대조군은 실제 어댑터의 풀 시간 초과를 사용했고, 이 경우에는 원래 작업을 임시 대기로 보존했다.

오류 코드는 [PostgREST 공식 오류 정의](https://docs.postgrest.org/en/stable/references/errors.html) 및 설치된 `@supabase/postgrest-js`의 오류 반환 처리를 확인했다. [Supabase 변경 이력](https://supabase.com/changelog)을 확인했고 이 수정에 새 SDK API·DB 정의·권한 변경은 필요하지 않았다. Markdown 이력 주소를 가져오지 못해 HTML 이력으로 확인했다.

## V2 — 진행 중인 원고와 탐색 후보의 차이를 연결

`operating-refresh.js`의 공통 범위 투영을 **현재 근거 유효성 검사와 자료 변경 판정 양쪽**에서 사용한다. `operating-cycle.js`는 등록된 입력의 결합·통화·스냅샷·사건을 확인한 다음 그 입력에 연결된 기사 URL로 두 검사의 범위를 맞춘다.

| 변화 | 진행 중인 원고 처리 |
|---|---|
| 사용하지 않은 기사의 반려/철회 판정만 변경 | 원래 작업에서 남은 검토 재개 |
| 새 미사용 기사 발견 | 새 탐색 자료는 보존하고 현재 원고의 검토를 이어감 |
| 사용한 기사 자체의 본문/판본 수정 | 기존 자료 변경 중단/새 입력 판정 유지 |
| 사용한 근거 철회·충돌·재검토 필요 | 기존 현재 유효성 차단 유지 |
| 기준환율 판본 변경 | 기존 가격 변경 중단 유지 |
| 현재 가격/사용한 자료 조회 불완전 | 이전 자료를 새 정상 자료로 가정하지 않고 대기 |

범위가 확정되지 않은 작업은 기존 전체 자료 검사를 사용한다. 기준환율·공식 통계 변경 판정과 출처 이용 조건 검사는 계속 별도 경로에서 적용한다. 뉴스 범위를 좁힌 것을 근거·이용 범위·가격 기준 완화로 사용하지 않는다.

6통화의 일회 정책 합성 흐름에서 “기사 A 채택·B 반려 → A만 사용한 원고 작성 → 검토 대기 → B 철회”를 확인했다. 같은 배치·같은 집필 입력에서 검토 1회만 실행되고 중복 작성/두 번째 배치는 없었다. 사용한 기사 A를 철회하는 기존 검사와 실제 가격 변경 검사도 유지했다.

기존 `continuation-recovery.test.ts`의 “자료 판본 변경” 검사는 실제로는 같은 출처의 수정이 아니라 **새 URL 기사 추가**를 입력했다. 그 한 검사를 미사용 새 기사 추가/사용한 기사 수정의 두 조합으로 명확히 나눴다. 앞 조합은 원래 두 국가의 검토만 재개하고 집필 입력을 보존한다. 뒤 조합은 영향을 받는 국가의 기존 원고를 계속 중단하며, 영향을 받지 않은 다른 국가의 검토는 진행한다. 필수 차단 기대값을 삭제하지 않았다.

## 실제 격리 저장 경로

`supabase_db_latamfx-2x-isolated`, 포트 56322만 사용했다. 실제 `createRuntimeStore`와 설치된 SQL 함수를 SQL 클라이언트로 연결했고, 기사·모델 응답은 합성이다. Supabase HTTP 연결 시험은 아니다.

| 시나리오 | 추가 모의 호출 | 결과 |
|---|---:|---|
| 저장 표현 손상 2회 → 복구 → 미사용 기사 철회 | 1 | 손상 중 0회/복구 필요, 복구 뒤 원래 일회 배치에서 검토만 1회. 원래 집필 입력 해시·작성 작업 1개 유지 |
| 사용한 근거 철회 | 0 | 원래 검토 차단 유지 |
| 준비 조건 복구 + 다른 국가 조회 장애 | 4 | 복구된 국가만 추출·대조·집필·검토, 반복 시 추가 0 |
| 사용한 근거 철회 → 명시적 재승인 | 1 | 이전 작성 응답을 유지하고 검토만 재개 |

모든 시험 쓰기는 롤백했고 대상 테이블/제어의 전후 해시가 같았다. 시퀀스 불변까지 주장하지 않는다. DB 함수·테이블·권한·migration은 변경하지 않았다.

일회 시험은 원래 배치의 검토 완료 뒤, 자료 풀이 달라진 새 배치를 추가로 요청하면 계속 `one_time_scope_or_expiry_hold`로 차단한다. 기존 승인 범위를 넓히지 않았다는 뜻이다. 이번 수정은 원래 작업을 불필요하게 종료하지 않아 **남아 있던 검토를 먼저 완료**하도록 한 것이다. 실제 사용하지 않은 추가 승인이나 재시도는 없다.

## 보존·한계·다음 단계

- 과거 실제 원문 처리 요청 21건을 동일 해시로 재현했고 기존 입력/원고/비용을 담은 4파일의 해시가 유지됐다. 알려진 MXN 과거 판정의 현재 재사용 보류도 유지했다.
- 전체 1,240검사는 1,057개 선언과 183개 매개변수 확장을 포함한다. 중복 이름·정확히 같은 본문·자명한 자기 비교 탐지 결과는 비어 있다. 의미적 중복 부재나 원고 품질 1,240건을 뜻하지 않는다.
- 리포트 전용 빌드의 기존 `src/local-report/dbClient.ts` 정적/동적 중복 import 경고는 남아 있다. 이번 서버 경로 변경과 관련된 새 빌드 오류는 없다.
- 화면/브라우저 흐름은 변경하지 않았으며 이번에 UI 클릭·인쇄를 다시 검사했다고 보고하지 않는다.

다음은 최신 무료 탐색부터 6통화 공통 입력·보류 사유·총 비용 상한을 준비하는 단계다. 실제 새 모델 호출은 별도 예산 승인 범위에서 진행하고, 원고 품질은 그 결과로 평가한다. 이번 결함 보완 뒤에 같은 목적의 코드 점검을 이유 없이 반복하지 않는다.
