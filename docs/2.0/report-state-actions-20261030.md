# 리포트 상태·행동표 — 독자와 관리자 공통 계약

> 후속 실제 검증: [기존 앱 로컬 동선 결과](app-flow-verification-20261030.md). 승인·로그아웃·공개/캐시·조회 장애·철회를 재현했다. 철회/미존재 안내 혼동과 복구 후 관리자 오류 문구 잔존은 미해결이다. 아래 구현 대조표는 이 실제 결과와 함께 읽는다.

2026-10-30 · UI 검토 기준 확정 · 기존 로컬 구현 대조 · 새 UI/운영 미반영

## 적용 원칙

여섯 통화에 같은 표를 적용한다. 국가별 차이는 출처·가격 정의·달력·지표 정의에서 관리한다. 새 보고서의 **조사 상태**, 원고의 **게시 상태**, 화면의 **조회 상태**는 서로 다른 값이다. ‘자료 부족’이라고 기존 정상 보고서까지 오류로 만들지 않고, 조회에 성공했다고 근거·승인이 완료된 것으로 만들지 않는다.

독자는 마지막 유효 공개본만 읽는다. 기준일·관측일·게시일·최근 확인일을 구분하며 기존 원고의 날짜/본문/차트는 고정한다. 관리자도 품질 미검증·자료 누락·권한 실패를 승인 버튼으로 우회할 수 없다. 내부 원문·초안·검토자·상세 오류·비용 기록을 공개 상태 문구에 포함하지 않는다.

아래 문구는 **의미와 행동의 확정 계약**이다. 정확한 글꼴·배치·최종 짧은 문구는 UI2.0에서 다듬을 수 있다. ‘연결 필요’는 완료되지 않은 항목이다.

## 상태가 겹칠 때의 우선순위

1. **권한 실패는 관리자 비공개 화면을 먼저 비운다.** 공개본 조회 권한과 혼동하지 않는다.
2. **알려진 철회·공개 중지 정보가 캐시보다 우선**한다. 서버가 뒤늦게 옛 성공 응답을 주어도 같은 철회 ID를 되살리지 않는다.
3. **조회 실패는 미발행과 다르다.** 정상 응답이 없으면 ‘보고서 없음’을 단정하지 않는다. 허용 캐시가 있을 때만 명시적으로 대체 표시한다.
4. **조사 상태는 기존 공개본 옆의 정보**다. S03~S09 때문에 기존 날짜/본문을 새 날짜로 바꾸지 않는다. 점검 정보 자체도 오래됐으면 확인 시각을 표시한다.
5. **직접 지정한 과거 원고는 자동 최신 대체하지 않는다.** 다른 유효본으로 이동하는 링크는 제공할 수 있다.
6. **알 수 없는 상태는 정상으로 추정하지 않는다.** 내부 상태를 그대로 공개하지 않고 안전한 공개 응답에 없는 값은 ‘상태 확인 불가’로 다룬다.

## 함께 읽을 예외

- 철회 직후 DB도 장애: 이미 철회를 확인한 ID는 차단한다. 다른 정상 캐시가 있으면 그 보고서의 날짜/캐시 상태를 명시한다. 아무 클라이언트도 아직 철회 정보를 받지 못한 완전 오프라인 상황에서 즉시 철회가 전파됐다고 보장할 수는 없다.
- 현재 로컬 캐시 상한 24시간·게시 상태 재확인 15분은 `report-data-policy.js`의 **로컬 시험값**이다. 보존/경보 제안과 마찬가지로 운영 수치 승인·적용 완료가 아니다. 운영에서 허용할 철회 전파 지연과 공개 상태 응답을 별도로 확정해야 한다.
- ‘부분 근거 부족’이라도 확인된 비교·설명과 부족 범위를 분명히 구분한 짧은 점검본은 내용 검토 대상으로 삼을 수 있다. 핵심 확인이 전부 안 되거나 조회가 실패한 것을 정상 점검본으로 만들지는 않는다.
- 가격 기준점은 순수한 최신 게시 순서와 다르다. 정책 전용 글·역사 사례·문체 편집·정정만 한 판본은 환율 점검 시계를 다시 시작하지 않는다.

이번 19개 기존 자동 사례 통과는 공개 선택·캐시·주기 계약 검증이다. DB 권한/RPC·브라우저·운영 환경 합격으로 확대하지 않는다.

다음 **Sol High 로컬 기능 확인**에서는 S01/S02/S08/S11/S13~S16을 기존 원고와 격리 환경으로 확인하고 차이를 기록한다. 새 UI 구현에 앞서 상태를 더 늘리기보다 위 표의 빠진 연결을 한 묶음으로 다룬다. UI2.0에서는 독자 화면을 단순하게, 관리자에게만 원인·대기 항목·조치 버튼을 자세히 보여준다.
