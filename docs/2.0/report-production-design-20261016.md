# LATAM FX 리포트 조사와 판단과 제작 종료 설계

2026-10-16 · 설계안 · 구현 및 유료 실행 전

## 설계의 결론

리포트 제작을 **조사 → 근거 검토 → 집필 → 문장 검토 → 관리자 승인**으로 나눈다. 검색은 집필 모델 내부에 넣지 않고 별도 수집 코드가 수행한다. 의미 판단에는 제한된 AI 검토를 연결하되, AI의 판정을 게시 승인으로 사용하지 않는다.

초기 완성 목표는 ‘Codex가 매번 자료를 찾아 입력을 만들고 문장을 고치지 않아도, 운영 작업이 검토 가능한 초안을 만들거나 보류 이유를 반환하는 상태’다. 관리자의 채택 판단은 남긴다. 무인 자동 게시, 메일 변경, 전체 2.0 출시는 별도 범위다.

이 설계는 [현재 칠레 제작 과정](report-creation-flow-20261016.md)과 [질문 중심 자료 탐색 설계](question-led-evidence-discovery-design.md)를 연결한다. 아래 상한과 판단 방식은 제안이며, 기존 설정이나 과거 승인을 변경하지 않는다.

## 1 조사 설계

### 1.1 조사할 이유와 보고서 목적

기존 가격·사건 판정기를 유지한다. 새 가격 관측, 실제 경제 발표, 중요한 수정·반대 근거가 조사 계기다. 예정 일정은 준비 신호일 뿐 발표 완료나 집필 자격이 아니다.

코드가 사건 종류에 맞는 목적을 먼저 제안한다. 모호하거나 여러 목적이 경쟁하면 검토 대기로 둔다. 모델이 자료 부족을 숨기기 위해 목적을 바꾸지 못하게 한다.

| 목적 | 핵심 독자 질문 | 집필 전 필요한 근거 | 없어도 되는 부분 |
| --- | --- | --- | --- |
| 환율 움직임 설명 | 무엇이 얼마나 움직였고 어떤 배경이 확인되는가? | 비교 가능한 환율 관측, 같은 움직임을 설명하는 원문, 사건·기사·가격의 시간 관계, 주요 다른 설명 검토 | 직접 관련 없는 월별 소비 지표 |
| 정책 업데이트 | 결정·성명에서 무엇이 달라졌고 어떤 조건이 붙는가? | 실제 공식 발표와 비교할 이전 발표, 적용 시점·조건, 해당 국가와의 관계 | 발표 이후 환율을 아직 확보하지 못했다면 실제 시장 반응 설명 |
| 경제·소비 환경 업데이트 | 전체와 관련 상품군·구매 여건에서 무엇이 달라졌는가? | 공식 지표와 기간·비교 기준·정의, 선택한 비교를 지지하는 자료 | 선택하지 않은 금융·소득 주제 |

환율 움직임 설명에서 가격 관측시각이 부족하면 저장 환율의 직접 원인 단정을 허용하지 않는다. 기사에 귀속한 시장 배경은 별도 범위로 검토할 수 있다. 핵심 질문에 답할 수 없다면 보류하며, 통계 보고서로 자동 전환해 ‘성공’ 처리하지 않는다.

### 1.2 질문을 먼저 정하고 검색한다

초기에는 등록된 질문과 지표 정의를 사용한다. 조사 계획을 만들기 위한 별도 AI 호출은 기본 경로에 넣지 않는다. 질문마다 다음을 고정한다.

- 독자가 알고 싶은 것과 선택 이유.
- 필요한 국가·기간·지표·상품·채널·비교 기준.
- 필수 질문인지 선택 질문인지.
- 답이 충분한 상태와 비교 불가능한 상태의 기준.
- 먼저 찾을 출처와 대체 경로.

선택 보충 질문은 최대 두 개이며, 개수를 채우지 않는다. ‘좋아졌다’는 결론을 검색어에 넣지 않고 증가·감소·정체·불일치에 같은 채택 기준을 적용한다.

예를 들어 실질 시간당 보수만 있다면 같은 기간의 소매를 찾고, 소매가 있다면 관련 상품군과 전체를 비교한다. 소비자 금융을 설명할 자료가 없으면 정책금리만으로 할부 구매 여건을 단정하지 않는다.

### 1.3 자료를 가져오는 순서

1. 저장된 원문과 검토 결과를 확인한다. 동일 출처·기간·범위·버전의 자료는 재사용한다.
2. 등록된 공식 발표 목록·API·파일을 확인한다. 최신성은 자료 주기와 발표 일정에 맞춰 판단한다.
3. 부족한 질문만 허용된 뉴스 검색 경로로 보충한다. 현재 GDELT와 현지 사이트맵 수집기를 재사용한다.
4. 검색 결과의 원문과 표·주석을 확보한다. 제목과 검색 요약은 발견용이지 확정 근거가 아니다.
5. 원문을 정리하고 날짜·통계 범위를 확인한 뒤 근거 검토에 넘긴다.

외부 검색과 Sonnet 집필은 다른 단계다. 검색기는 URL·원문을 확보하며, Sonnet에는 채택된 자료만 전달한다. 집필·교정 중 숨은 검색이나 임의 URL 추가를 허용하지 않는다.

### 1.4 출처 등록과 운영 제한

CLP는 현재 검토한 INE 소매·보수 자료부터 연결한다. CLP 정책·소비자신용, BRL·MXN의 각 지표는 출처별 이용 조건·시리즈 정의·추출 가능성을 확인한 뒤 등록한다. 기존 어댑터가 있다는 사실만으로 운영 수집이 준비됐다고 처리하지 않는다.

출처 등록에는 접근 주소, 허용 호스트, 인증 여부, AI 입력·공개 인용 가능 범위, 주기, 시리즈·분류 코드, 추출 방식, 최근 성공·실패, 변경 확인 방법과 담당 검토 기록을 둔다. 새로운 이용 조건 판단이나 새 출처 승인은 AI에게 맡기지 않는다.

등록된 구조에서 수치를 추출하고 교차 확인하는 것은 자동화한다. PDF 표 구조·산식·분류가 바뀌었거나 추출값이 모순되면 사람의 검토로 보낸다. 비전 모델이나 유료 검색을 자동 대체 경로로 추가하지 않는다.

### 1.5 검색 배분과 정지 기준

기존 판정기는 질문별 요청을 만들지만 실제 수집기는 고정 질문 순서와 기존 URL 우선 순서를 사용한다. 질문 계획을 수집기에 전달하고, 보유 원문 재확인과 새 질문 탐색의 슬롯을 분리해야 한다.

초기 제안은 기존 탐색 설계의 검색 4회·원문 최대 6개·전체 HTTP 12회·전체 수집 120초·개별 응답 2MB·총 응답 12MB다. 모든 출처가 이 크기에 맞는다고 가정하지 않는다. 초과는 제한 사유를 남기고 수동 확인으로 보낸다.

필수 미해결 질문을 먼저 충족시키고, 남은 범위에서 선택 질문별 슬롯을 배분한다. 기존 설계의 ‘선택 질문 최초 슬롯 우선’보다 **집필 자격을 막는 필수 질문 우선**으로 정교화한다. 경제 업데이트에 환율 전용 필수 질문을 붙이지 않으므로 소비 질문이 뒤로 밀리는 문제는 목적별 선택으로 해결한다.

채택 근거가 충분하고 중요한 반대 조건 확인을 마치면 상한을 채우지 않고 종료한다. 자료 충돌이 남으면 기사 수를 늘려 다수결하지 않는다. 요청 실패도 상한에 포함하며, 실행 ID를 바꿔 같은 조사의 한도를 초기화하지 않는다.

## 2 판단 설계

### 2.1 코드와 AI와 관리자의 책임

| 판단 | 코드 | AI 검토 | 관리자 |
| --- | --- | --- | --- |
| 날짜·수치·비교 가능성 | 형식·범위·산식·버전 확인 | 주석과 의미상 범위의 모순 지적 | 미등록 정의·추출 오류 해결 |
| 원문이 주장을 지지하는가 | 인용 위치·원문 일치·ID 검사 | 원문의 지지·제한·모순·미확인 판단 | 중요 쟁점과 미확인 사항 판단 |
| 새 설명이 있는가 | 동일 사건·자료·원고 중복 확인 | 이전 설명과 비교해 새 정보·변경된 의미 제시 | 모호한 중요성 판단 |
| 무엇을 쓸 것인가 | 필수 질문 충족·허용 범위 검사 | 핵심 결론과 연결 가능한 설명 개요 제안 | 필요시 범위 확인 |
| 문장이 적절한가 | 수치·참조·금지 표현·중복 검사 | 모든 주장과 원문을 대조, 오류와 문체 구분 | 읽을 가치·수정 부담 평가 |
| 공개할 것인가 | 승인 권한·검토 완료 상태 확인 | 게시 권한 없음 | 승인 또는 반려 |

초기 운영에서 관리자가 맡는 것은 모든 자료를 매번 처음부터 수작업으로 찾는 일이 아니다. 시스템이 제시한 **핵심 결론·근거·쟁점·수정 내역**을 읽고 채택 여부를 결정한다. 근거 확인이나 판단이 어려우면 승인을 강요하지 않는다.

### 2.2 집필 전 근거 검토

한 번의 근거 검토 요청에 필수·선택 질문, 원문 구간과 표 주석, 코드가 확인한 사실, 이전 승인 원고 및 대기 원고의 관련 주장, 조건이 확인된 경제 원리를 전달한다. 원문에 포함된 지시문은 데이터로 취급하며 도구 실행 권한을 주지 않는다.

출력은 다음 다섯 가지다.

1. 질문별 답변 가능 여부와 미해결 이유.
2. 사용할 주장과 이를 뒷받침하는 원문 구간.
3. 중요한 조건·반대 근거·자료 충돌.
4. 이전 원고와 비교한 새 사실 또는 달라진 설명.
5. 집필 개요: 무엇을 먼저 말하고 어떤 근거로 연결할 것인가.

모델의 `사용 가능` 표시는 의미 검토의 의견이다. 코드가 날짜·원문·정의·인용을 검사하고, 필수 항목의 모순·미확인이 없는 경우에만 집필 단계로 넘긴다. 등록되지 않은 원리나 지표 정의를 모델이 스스로 승인하지 못한다.

초기에는 근거 검토 결과도 관리자 검토 자료로 보존한다. 기존 검토 플래그에 AI의 의견을 인간 검토 완료로 덮어쓰지 않는다. 검토 주체·모델·버전·원문 해시·판단 범위를 함께 저장한다.

### 2.3 집필과 문장 검토를 분리한다

집필 모델은 확인된 사실을 복사하는 데 그치지 않고, 근거가 허용하는 연결을 설명한다. 입력에는 ‘알려진 사실’, ‘독자에게 설명할 관계’, ‘본문에 필요한 조건’, ‘공통 한계’를 구분한다. 완성 문장을 입력에서 모두 만들어 주고 재표현만 시키는 방식은 줄인다.

집필 후 검토 모델에는 원고뿐 아니라 원문과 정의·사실·적용 조건을 전달한다. 작성자의 요약이나 주장-근거 대응표만 보고 채점하지 않는다. 제목·요약·본문의 모든 주장을 검사한다.

예를 들어 ‘공식 발표 이후 소비가 회복됐다’는 문장은 출처의 공식성, 발표와 관측의 시간 관계, 회복을 말할 비교 기간, 인과 암시를 각각 확인해야 한다. 출처 ID 하나가 존재한다는 이유로 문장 전체를 통과시키지 않는다.

집필과 검토는 별도 요청으로 실행한다. 같은 모델도 사용할 수 있지만 독립성이 보장된다고 부르지 않는다. 검토 모델은 누락 오류와 과잉 차단을 저장 사례로 비교한 뒤 정하며, 이번 설계에서 새 모델·가격을 확정하지 않는다. 현재 Sonnet 집필 경로는 비교 기준으로 유지한다.

### 2.4 판단 결과의 공통 분류

| 결과 | 의미 | 처리 |
| --- | --- | --- |
| 근거가 지지함 | 주장 전체가 원문·사실·조건과 맞음 | 유지 |
| 표현 개선 | 내용은 맞으나 제목·반복·문장이 불명확함 | 선택 개선. 이것만으로 유료 교정하지 않음 |
| 필수 교정 | 일부만 지지되거나 범위·인과·기간을 잘못 확대함 | 같은 근거로 고칠 수 있을 때만 제한 교정 |
| 판단 불가 | 원문·시각·정의 등 핵심 확인이 부족함 | 자료 대기 또는 관리자 검토. 거짓으로 단정하지 않음 |
| 충돌 | 신뢰할 만한 자료끼리 모순되거나 수정본 관계 불명확 | 영향받는 주장 보류. 여러 모델의 다수결로 해결하지 않음 |

평가 점수는 이 분류를 대체하지 않는다. 평균 4/5·근거 충실도 4/5 이상이어도 중대한 오류나 필수 미검증이 있으면 승인 후보가 아니다. 점수·검토 주체·규칙 버전을 분리하고 관리자 평가와 AI 점수를 합쳐 평균내지 않는다.

## 3 종료와 교정과 비용 설계

### 3.1 유료 호출을 하기 전에 멈출 조건

- 관측 데이터가 잘못됐거나 핵심 원문·이용 조건·비교 정의가 확인되지 않았다.
- 같은 사건과 설명의 승인본 또는 검토 대기본이 이미 있다.
- 새 자료는 있지만 같은 수치를 반복할 뿐 독자 질문에 새 답을 주지 않는다.
- 예산이 없거나 이전 호출의 비용이 미확인이다.

정확한 중복은 코드로 중지한다. 의미상 중복 여부가 모호한 경우에만 승인된 예산 안에서 근거 검토를 사용할 수 있다. ‘모든 중복을 무료로 자동 판단한다’고 보장하지 않는다.

### 3.2 제작 상태와 다음 행동

| 상태 | 뜻 | 다음 행동 |
| --- | --- | --- |
| 조사 후보 | 변화나 발표가 감지됨 | 질문 선택·자료 점검 |
| 근거 대기 | 핵심 자료 부족·충돌·추출 실패 | 원인이 해소될 때 재개. 집필 없음 |
| 추가 설명 없음 | 이전 원고 대비 읽을 새 내용 없음 | 이전 공개본 유지 |
| 집필 가능 | 근거와 필수 질문 검토 완료 | 예산 확인 후 집필 |
| 원고 검토 중 | 초안 저장·검사 중 | 원문 대조 |
| 교정 가능 | 현재 근거만으로 필수 오류를 바로잡을 수 있음 | 승인된 교정 한도가 있으면 1회 |
| 관리자 대기 | 자동 검사·내용 검토를 마친 승인 후보 | 관리자 평가·승인·반려 |
| 보류·실패 | 품질 미달·미확인·기술 실패 | 이유 보존. 날짜만 바꿔 재생성하지 않음 |
| 승인됨 | 권한 있는 관리자가 검토한 정확한 사본 승인 | 공개 복사 |

자료 상태·작성 자격·원고 품질·게시 상태는 내부적으로 별도 유지한다. 위 상태는 사용자가 진행을 이해하기 위한 요약이지 네 판단을 하나의 통과 값으로 합친 것이 아니다.

### 3.3 교정은 한 번만 제한적으로

교정은 새 조사나 전체 재작성 대신 확인된 문장의 오류를 고치는 작업이다. 대상 문장, 이유, 사용할 근거, 바꾸면 안 되는 사실을 지정한다. 필요한 자료가 없으면 교정 모델에게 상상으로 채우게 하지 않는다.

교정본은 새 사본이다. 원문·이전 비용·이전 점수를 보존하고 새 사본 전체를 다시 검사한다. 수정 문장만 확인하면 제목·요약과 충돌을 놓칠 수 있기 때문이다.

문체 개선만 있으면 기본적으로 관리자에게 제시하고 유료 교정하지 않는다. 자동 교정을 한 번 거친 뒤에도 필수 오류가 남으면 종료한다. 검토 실패를 다른 모델 호출이나 규칙 완화로 우회하지 않는다.

### 3.4 호출과 비용 상한

| 단계 | 제안 최대 호출 | 목적 |
| --- | --- | --- |
| 근거 검토·개요 | 1회 | 원문 지지와 새 설명 확인 |
| 집필 | 1회 | 원고 작성 |
| 문장 검토 | 1회 | 오류와 문체 개선 구분 |
| 필수 교정 | 조건부 1회 | 같은 근거로 고칠 수 있는 오류만 수정 |
| 교정본 재검토 | 교정 시 1회 | 전체 원고의 정합성 확인 |

새 원고의 기본 경로는 최대 3회, 교정까지 승인한 경로는 최대 5회다. 모두 별도 승인 예산 안에서만 실행한다. 유효한 기존 근거 검토가 있으면 재사용할 수 있지만 자료·질문·규칙이 바뀌면 그대로 사용하지 않는다. 이 숫자는 이번 호출 승인이 아니다.

예산은 집필 한 번의 과거 비용이 아니라 **근거 검토 + 집필 + 검토 + 조건부 교정·재검토**를 기준으로 산정해야 한다. 실제 단가는 시험 준비 시 확인하며, 모델별 입력 상한과 추론을 포함한 출력 상한으로 계산한다.

필수 검토 비용까지 예약할 수 없으면 집필을 시작하지 않는다. 교정 예산이 없으면 오류 원고를 보류할 뿐 검토를 생략하지 않는다. 자동 재시도·자동 모델 교체는 기본 0회다. 비용 미확인 요청은 예약을 유지하고 같은 제작 작업의 추가 유료 호출을 중지한다.

## 4 기존 코드의 재사용과 연결 변경

| 영역 | 재사용 | 새로 연결하거나 보강할 부분 |
| --- | --- | --- |
| 가격·사건·이전 판단 | `generation-decision.js` | 승인본뿐 아니라 대기·실패 기록과 제작 실행을 한 사건에 연결 |

| 승인·공개 조회 | 기존 로컬 승인·A안 경로 | 자동 제작 결과를 초안으로 연결. 운영 배포는 별도 |

별도의 하네스를 한 세트 더 만들지 않는다. 기존 함수의 책임은 유지하고 순서와 데이터 전달을 관리하는 제작 실행기를 추가하는 방향이다. 과거 원고를 새 규칙으로 자동 승격시키지 않는다.

검토 계약의 호환성도 먼저 확인해야 한다. 예를 들어 현재 질문 판정기는 정책 업데이트를 구분하지만 문장 검토 준비 함수는 환율·경제 업데이트를 명시적으로 허용한다. 정책 원고를 경제 원고로 위장해 통과시키지 않고, 지원 계약을 구현·검증하기 전에는 검토 대기로 둔다.

## 6 구현 전에 확정할 계약과 검증 순서

### 먼저 고정할 계약

제작 작업은 통화·목적·사건·기준시점·자료 버전·규칙 버전으로 식별한다. 기준시점에는 시간대가 포함되어야 하며 발표시각·관측시각·수집시각을 섞지 않는다. 날짜만 확인된 발표로 장중 선후관계를 만들지 않는다.

각 단계는 입력 해시, 출력 위치, 사용 버전, 담당 주체, 상태, 이유, 요청·실제 비용, 다음 가능한 행동을 남긴다. 재개는 완료 단계의 유효성을 확인한 뒤 수행한다. 키·관리자 정보·내부 기록은 모델 입력과 공개 콘텐츠에서 제외한다.

외부 문서는 신뢰하지 않는 자료다. 허용된 호스트·프로토콜·응답 크기·타임아웃을 수집 코드가 강제하고, 임의 리디렉션·내부 주소 접근·인증정보 전달을 차단한다. 프롬프트의 경고 문장만으로 보안을 맡기지 않는다.

### 실행 순서와 완료 조건

1. **무비용 연결 설계의 코드화:** 질문 계획 → 수집 요청 → 결과 상태를 저장 자료와 모의 응답으로 연결한다. 누락 자료를 성공 처리하지 않고 동일 입력의 계획을 재현해야 한다.
2. **CLP 출처 갱신 연결:** 검토된 공식 출처의 새 발표·수정본·추출 실패를 다룬다. 실제 외부 접근은 범위를 알리고 수행하며, BRL·MXN 미지원 상태는 유지한다.
3. **근거·문장 검토 연결:** 저장 원고와 모의 AI 응답으로 지지·충돌·미확인·과잉 차단을 검사한다. AI의 의견이 관리자 승인으로 바뀌지 않아야 한다.
4. **제작 실행과 비용 연결:** 호출 전후 장애·중복·미확인 비용·재개·교정 한도를 모의 시험한다. 유료 호출은 아직 하지 않는다.
5. **별도 승인된 실제 종단 시험:** 한 사례에서 수동 입력 손질 없이 자료부터 검토 초안까지 실행하고 비용·오류·수정 부담을 확인한다. 기존 실패 사례와 조용한 날·근거 부족 사례도 평가한다.
6. **관리자 승인 흐름과 파일럿:** 사용자는 원고와 근거·쟁점을 보고 승인한다. 실제 운영 연결·기존 파일럿 기준·전체 2.0 출시는 별도 체크포인트를 유지한다.

테스트는 계산·검색 배분·의미 검토 응답·예산·승인의 책임별로 나눈다. 같은 계약을 여러 테스트 파일에서 반복하지 않는다. 실제 원문이 문장을 지지하는지와 읽을 가치는 내용 평가로 확인하며 자동 테스트 수에 합산하지 않는다.

## 7 완료를 판단하는 기준

기능 완성은 ‘한 원고의 점수가 4.0’이 아니라 다음을 모두 만족하는 상태다.

- 등록된 자료와 사건에서 시작해 Codex의 수동 파일 수정 없이 초안 또는 설명 가능한 보류 결과를 만든다.
- 모든 핵심 주장에 원문·기간·정의를 추적할 수 있다.
- 새 정보가 없는 날에는 불필요한 집필을 하지 않는다.
- 원고 실패·검토 실패·비용 미확인·중복 실행에서 상한을 지킨다.
- 수동 손질 전 원고와 교정 부담을 기록하며, 과거 편집본을 새 자동 생성 성공으로 세지 않는다.
- 관리자 승인 전에는 초안이 공개되지 않고 기존 환율 서비스와 승인본이 유지된다.

이번 설계로 확정한 방향은 검색과 집필 분리, 기존 도구 재사용, 단계별 판단 기록, 제한 교정, 관리자 승인 유지다. 실제 검토 모델·총예산·운영 주기·검토 담당자·배포 시점은 실측과 운영 승인에서 확정한다. 이번 설계는 추가 유료 호출이나 운영 변경의 승인이 아니다.
