## 결론

**다음 유료 전체 시험으로 넘어가기 전에 공통 실행 경로를 보완해야 한다.** 앞선 구현 보고의 ‘재개 연결 완료’는 기사 대조의 특정 고정 배치 시험에 한정된다. 원고 검토 장애, 다른 나라 자료 갱신, 판정 충돌까지 포함한 무인 운영 완료로 해석하면 안 된다.

- 외부 HTTP/모델 호출, 신규 비용, DB 연결/쓰기: 모두 0.
- 산출물: 이 점검서, 진행표 갱신, 비공개 재현 스크립트·결과.
- 기존 관련 검사 4파일 33사례는 모두 통과했으나, 아래 별도 장애 재현에서 공백을 확인했다. 검사 통과 수를 원고 품질이나 자동화 합격률로 사용하지 않는다.

## 먼저 고칠 문제

### A1 · 높음 — 원고를 쓴 뒤 검토 서버가 일시 실패하면 이어지지 않는다

**재현:** 메모리 저장소와 합성 응답만 사용하되 `testOnly:false`로 실제 작업 식별 규칙을 적용했다. BRL의 원고 작성 성공 후 원고 검토 사전 확인에서 한 번만 장애를 냈다. 최초 결과는 `content_review_hold`, 사건은 `held`, 배치는 완료가 됐다. 장애를 해제한 같은 실행에서도 새 모의 호출은 0이며 검토가 이어지지 않았다.

**원인:** `runtime.js:218`은 검토 사전 확인 실패도 `review_output_hold`로 묶는다. `:228`에서 작성 작업을 완료 처리하고, 최상위에는 `content_review_hold`만 돌려준다. `runtime-batch.js`는 `generated.cost.reviewStatus/reviewReason`을 후속 판단에 넘기지 않는다. `operating-cycle.js:132`는 이 사건을 일시 대기 대신 최종 보류로 저장한다. 작성 응답 재사용은 `runtime.js:173`에서 `received` 상태만 허용하므로 단순히 배치만 다시 열어도 충분하지 않다.

**처리:** 추출·대조·집필·검토 각각의 완료/전송 전 장애/전송 후 비용 미확인/내용 반려를 구분한다. 전송 전 일시 실패에는 작성 응답을 보존하고 검토 단계만 재개한다. 내용 반려를 자동 재시도로 바꾸지는 않는다.

**합격 기준:** 6통화 각각 검토 직전 장애 → 나머지 통화 진행 → 복구 후 해당 검토 1회, 집필 추가 0회. 검토 이후 저장 장애도 중복 원고 없이 별도로 재현한다.

### A2 · 높음 — 다른 나라의 새 자료 때문에 중단된 나라가 재개되지 않는다

**재현:** COP 추출은 성공하고 대조 사전 확인만 일시 실패시켜 배치를 `paused`로 만들었다. 두 번째 실행에서는 COP 자료를 그대로 두고 BRL 기사만 한 건 추가했다. 전체 배치 식별값은 바뀌었고 COP는 `unchanged_case_already_processed`가 됐다. COP의 원래 사건은 여전히 `paused`, 대조 재개는 0회였다.

**원인:** `operating-cycle.js:58`의 배치 식별값은 6개국 자료 전체에 의존한다. `:68`은 새로 계산한 식별값 하나로만 이전 배치를 조회한다. COP 사건 식별값은 그대로지만 SQL의 사건 재개는 같은 배치일 때만 허용한다(`20261101090428_operating_reference_refresh_recovery.sql:192`). 실제 SQL을 읽어 조건을 대조했으며 이번에 DB에서 쓰기 시험을 한 것은 아니다.

**처리:** 국가별 미완료 작업 조회를 새 전체 배치 생성보다 먼저 수행한다. 기존 고정 요청을 원래 배치/예산 장부로 마무리할지, 새 입력 때문에 취소·대체해야 할지 명시한다. 새 자료를 과거 승인 입력에 끼워 넣거나 기존 비용을 새 배치로 옮겨 숨기지 않는다.

**합격 기준:** COP 일시 대기 중 BRL 새 기사, 기준환율 갱신, 한국 날짜 변경을 각각 넣어 재현한다. 재개 또는 명시적인 대체 대기가 되어야 하며, 설명 없이 ‘이미 처리됨’으로 남으면 실패다. 완료된 추출 재호출 0회와 원래 비용 장부 보존을 확인한다.

### A3 · 높음 — 보존된 성공 기록과 현재 사용 가능한 판정이 분리되지 않았다

**합성 재현:** 같은 원문에 성공 기록과 뒤이은 반려 기록을 모두 넣어도 `reuseOperatingSources`는 성공 기록을 선택했다. `operating-source-cache.js:83`이 성공을 항상 우선하기 때문이다. 성공 기록에는 반려 기록과 같은 `pipelineVersion` 필터도 적용되지 않는다. 새 규칙이 기존 판단에 영향을 주는지 판단할 연결이 없다.

**저장 실자료:** MXN 과거 비교 응답은 현물 18.7796이 같은 기사 내 장중 최저 18.8353보다 낮다는 문제를 적으면서도 `blocking:false`로 판단했다. 저장 재생 결과는 여전히 `input_staged`이고 저장 집필 입력에도 18.7796이 남아 있다. 실제 잘못된 새 보고서가 작성됐다는 뜻은 아니다. 알려진 문제를 문서에만 기록하면 자동 실행의 사용 가능 판정을 막지 못한다는 증거다.

**처리:** 원본 판단 기록은 불변으로 두고, 별도 유효성 상태(사용 가능/재검토 필요/철회/대체 관계)를 연결한다. 성공과 반려가 충돌하면 성공을 무조건 선택하지 않는다. 규칙 변경의 영향 범위를 버전으로 지정하고 해당 범위만 재검토한다. MXN 숫자나 과거 모델 응답을 손으로 고치지 않는다. 다른 적합한 근거는 계속 쓸 수 있어야 한다.

**합격 기준:** 과거 성공 → 모순 확인 → 사용 대기 → 독립 재검토 또는 대체 근거 채택의 전 과정을 같은 공통 규칙으로 재현한다. 문제 근거는 집필 입력에서 제외되고, 영향 없는 과거 성공은 불필요하게 재호출하지 않아야 한다.

## 함께 고칠 운영 문제

### A4 · 중간 — 프로그램 오류가 자료 부족에 가려지거나 다음 실행에서 경보가 사라진다

두 가지를 재현했다.

1. 같은 국가에 프로그램 오류와 근거 부족이 함께 있으면 `countryContinuation`은 내용 부족을 선택해 `find_other_evidence`만 반환한다. 종료 코드는 0이다. 원인을 고치지 않고 새 기사만 찾게 될 수 있다.
2. 최초 결과의 `await_pipeline_repair`는 확인 필요/종료 코드 2지만, 같은 결과가 `previousResult`로 반환되면 단순 대기/종료 코드 0이 된다. `operating-result.js`는 이전 결과의 상태 이름은 읽지만 `continuation`은 읽지 않는다.

**처리:** 후속 조사 행동과 해결해야 할 오류 목록을 별도로 보존한다. 기술·회계 오류는 다른 내용 부족으로 덮지 않는다. 이전 결과도 동일한 분류 함수를 거치게 한다.

**합격 기준:** 최초/캐시 반환의 오류 심각도·이유·종료 코드가 같고, 기술 오류가 남아 있어도 안전한 무료 탐색은 가능하되 미해결 오류가 운영자에게 계속 표시되어야 한다.

### A5 · 중간 — 과거 반려가 해결돼도 탐색 우선순위에는 계속 남는다

**재현:** 같은 URL의 과거 반려와 정상 대조 기록을 함께 넣어도 `researchFeedback`은 그 URL을 후순위로 두고 대체 색인 검색을 요청한다. 기록 전체에서 반려를 모으기만 하고, 현재 원문 판본과 유효한 판단을 구분하지 않는다.

**처리:** A3의 유효 판정을 재사용해 피드백을 계산한다. URL만이 아니라 본문 판본·검토 기준·해결 여부를 함께 본다. 해결된 반려는 감사 이력으로 남기고 현재 탐색 실패로 재집계하지 않는다. 반대로 오래된 성공이 새 수정본의 확인을 생략하게 해서는 안 된다.

**합격 기준:** 반려 → 같은 URL의 수정본 → 확인 통과 시 현재 피드백에서 해소되며, 그 뒤 다시 수정되면 별도 판본으로 확인한다.

## 기존 시험에서 놓친 이유

- 기존 재개 사례는 기사 대조의 일시 실패이며 원고 검토 장애가 아니었다.
- 같은 고정 자료·시각으로 재실행했으므로, 다른 국가 자료가 바뀌는 배치 간 연결을 검사하지 않았다.
- 공통 fixture의 기본 `testOnly:true`는 일부 식별·잠금 규칙이 실제 경로와 다르다. 이번 두 흐름 재현은 외부 호출 없는 메모리 저장소에서 `testOnly:false`를 사용했다. 운영 환경 활성화가 아니다.
- 반려 후 성공 기록의 공존은 확인했지만 성공 후 반대 판정, 해결된 반려의 탐색 피드백, 오류 결과 재조회는 검사하지 않았다.

따라서 기존 검사는 해당 범위에서 유효하지만 ‘모든 일시 실패 재개’나 ‘최신 유효 판정 선택’의 증명으로 확대할 수 없다.
