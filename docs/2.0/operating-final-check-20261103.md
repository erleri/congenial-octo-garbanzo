# 2.0 운영 전환 최종 점검 — 2026-11-03

## 판단

**최신 운영 환율을 보존한 로컬 출시 사본과 DB 업그레이드 검증은 통과했다. 운영 반영은 아직 하지 않았다.** 다음 작업은 수집·집필 규칙을 다시 늘리는 일이 아니라 운영 설정 확인, 운영 백업, 승인된 단계적 적용이다.

수신자는 사용자 결정에 따라 **기존 회사 배포 주소를 그대로 유지**한다. 운영 목록은 수정하지 않았다. 오늘 반송 원문에서 해당 주소의 `550 No such user`를 확인했으므로, 주소 유지 결정으로 실제 수신까지 검증됐다고 기록하지 않는다.

## 적용할 설정과 순서

아래는 준비값이며 현재 운영에 설정하지 않았다.

| 위치 | 준비할 항목 | 시작 상태 |
| --- | --- | --- |
| GitHub 변수 | `FX_REPORT_GENERATOR` | `currency` — 구 생성기와 배타 선택 |
| GitHub 변수 | `FX_REPORT_PUBLISH_MODE` | `review` — 관리자 승인 전 공개 금지 |
| GitHub 변수 | `FX_REPORT_EXECUTION_MODE` | `plan` — 무과금 |
| GitHub 변수 | `FX_REPORT_OPERATIONAL_HOLD` | `true` — 새 생성 잠금 |
| GitHub 변수 | `FX_REPORT_ENABLED` | 표시와 실행 선택을 명시. 현재 운영 생성파일 true를 꺼짐으로 가정하지 않음 |
| GitHub 변수 | `FX_EMAIL_REPORT_MODE`, `FX_EMAIL_SEND_APPROVED` | 코드 첫 적용은 `legacy`/`false`, 준비 후 `approved`/`false`로 새 발송을 보류하며 조회 확인 |
| GitHub 변수 | `FX_EMAIL_HOLD` | 실제 테스트/수신자 범위 확정 전 신규 발송의 중지에 사용. true면 기존 메일도 중지되므로 별도 승인으로 적용 |
| GitHub Secret | `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY` | 같은 운영 프로젝트. 서비스 키는 서버 job에서만 사용 |
| GitHub Secret | `OPENROUTER_API_KEY`, `INEGI_INDICATORS_TOKEN` | 실제 새 job의 등록 여부 확인. 로컬 설정됨과 구분 |
| 기존 GitHub Secret | `SMTP_USERNAME`, `SMTP_PASSWORD`, 기존 환율 API 키 | 현재 성공 경로 유지. 새 값을 요구하거나 교체하지 않음 |
| DB 실행 제어 | 생성/검토 enabled, 월 예산 | migration 직후 false/false/0 유지 |

기능 잠금 상태의 첫 적용과 유료 생성/새 메일 활성화는 서로 다른 승인 단계다. 전체 Daily workflow 수동 실행에는 기존 메일 발송이 포함되므로 ‘조회 시험’이라고 실행하지 않는다. 실제 runner 점검은 명시적으로 무발송 범위를 갖춰 수행한다.

운영에는 새 공개 원고가 아직 없다. 로컬 승인본을 migration이 자동 게시하지 않으며 테스트 검토 신원을 운영 승인으로 바꾸지 않는다. 첫 운영 원고의 생성·근거 검토·관리자 승인 후 해당 공개ID로 메일 링크를 확인한다.

메일은 **작성 마감 시점까지 승인·공개된 원고**만 소개한다. 새 생성 job은 기존 일일 메일 뒤에 분리돼 있고 관리자 승인도 필요하므로, 그날 뒤에 승인된 원고는 다음 일일 메일에서 소개된다. 즉시 별도 알림 메일을 자동 발송하는 기능은 이번 범위가 아니다.

## 중지·복구를 실행할 때

- DB 적용 전에는 실제 운영 백업과 기존 migration9개/파일 해시를 기록한다. 추가24개만 적용하며 자동 생성은 꺼둔다.
- 빌드·배포가 실패해 공개되지 않았으면 현재 정상 사이트를 유지한다.
- 공개한 코드에 문제가 있으면 새 생성·메일을 명시적으로 잠그고, 원인 변경을 되돌리는 커밋을 CI로 다시 배포한다. 이전 배포를 직접 재게시하는 절차와 혼용하지 않는다. 이 절차는 아직 실제 운영에서 실행하지 않았다.
- 코드의 이전 동작 복구를 위해 DB를 과거 백업으로 덮어쓰지 않는다. 새 계획값·승인/정정/철회·관리자 상태·발송/비용 장부를 보존한다.
- SMTP 결과가 불명확하면 메일 hold를 유지하고 근거로 조정한다. legacy로 바꿔 같은 메일을 다시 보내지 않는다.
- 새 메일7개 비공개 테이블도 용량·보존·백업 점검에 포함한다. 미확정 발송과 비용 기록은 자동 삭제 대상이 아니다.

Supabase의 실제 백업 제공 범위는 계정과 설정에 따라 확인해야 하며, DB 백업만으로 Storage 파일 본문까지 복구되는 것은 아니다. [공식 백업 안내](https://supabase.com/docs/guides/platform/backups)

기존 운영의 leaked-password protection 경고1개는 다시 확인했다. 이번 변경으로 새로 생긴 경고는 아니며, Auth 설정을 임의 변경하지 않았다. [설정 설명](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection)
