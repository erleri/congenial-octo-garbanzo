4. 용량·비용 산정

실측 평균·상위 사용량으로 월/분기/연간 전망을 만든다. 수집 횟수는 발행 횟수보다 많으므로 따로 계산한다.

  • 비공개 파일: 일일 신규 고유 자료 바이트 × 보관일 + 보호 자료 + 백업. 압축·중복 제거 효과는 실측 전 가정하지 않음.
  • DB: 카드·원고·상태·감사 기록 증가 + 인덱스 + 유지보수 여유. 서버 전체 용량과 테이블 데이터 크기를 혼동하지 않음.
  • 전송: 캐시를 고려한 실제 응답 크기 × 요청 횟수, Netlify와 Supabase를 따로 합산.
  • 배포: 코드 배포·데이터 갱신 배포를 분리. 대규모 데이터 변경에 따른 Git 이력 증가도 측정.
  • 알림/중단: 실제 한도 대비 경보·월말 예상 초과 경보·리포트 신규 수집/유료 생성 중단선을 확정. 저장이 가득 차기 전에 연구 작업을 멈추며 기존 서비스 여유분을 먼저 확보.

5. 복합 장애와 복구

  • 원문 개정 + 검토 대기: 새 판본을 저장하고 영향 원고만 재검토. 자동 수정/재발행 없음.
  • 모델 시간 초과 + 비용 미확인: 예약 보존, 자동 재시도 없음. 기존 환율·메일 계속.
  • DB 장애: 기존 FX 폴백 유지. 보고서 초안을 공개 캐시로 대신하지 않음.
  • 파일 저장 실패: 실행 미완료. 내용/승인 기록이 완성되지 않은 새 원고는 게시하지 않음.
  • 리포트 오류: 해당 리포트 철회 및 기능 중단, 기존 1.x 유지. 사이트 전체 복구는 1.x 회귀가 있을 때만.
  • 배포 복귀는 DB 복귀가 아님: 추가 스키마 호환 유지, 이후 계획환율 저장을 지우는 과거 DB 전체 복원 금지. 운영 복구는 새 쓰기와 감사 이력을 보존하는 절차로 설계.
  • 1.x 조회·계획환율 저장·메일에 회귀가 있으면 다음 단계 중단. 테스트 환경 복원만으로 운영 무손실을 보장한다고 보고하지 않음.

6. 출시 경계

출시 필수: 비공개 경계, 자료-승인 연결, 실패 격리, 용량 여유/경보, 정정 처리, 검증된 복구, 기존 기능 회귀, 6통화 자료 상태의 정직한 표시. 나중에 가능: 자동 삭제, 과거 전체 Git 자료 이전, 고급 저장 압축/관리 통계. 기존 전체 이력 이전과 보고서 출시를 하나의 변경에 묶지 않는다.

실제 새 모델 품질 시험·10영업일 파일럿·UI 2.0·전체 출시 판단은 원래 로드맵에 유지한다. 이 데이터 운영 보강은 출시 준비의 공통 작업이며 합성 테스트로 실제 품질/파일럿을 대체하지 않는다. 유료 호출, 유료 인프라, 운영 변경, 메일 변경은 각각 승인 범위를 지킨다.

근거와 제한

운영 계정·배포와 DB 크기/테이블 통계/Storage 개수는 연결 도구로 읽기 전용 확인. 로컬 크기·코드와 운영 SHA 내용의 완전 대조, 계정별 월 사용량, 실제 복원은 미완료. Supabase changelog.md는 도구/연결 오류로 읽지 못했으며 구현 전 재확인한다.

Supabase 백업 안내: Free는 별도 정기 내보내기·외부 백업을 권고하며 DB 백업에 Storage 파일 본문은 포함되지 않는다. Supabase 사용량 항목 · Netlify 요금제 · GitHub Actions 사용량
