# LATAM FX 데이터 보존·복구 절차

2026-10-30 · 로컬 검증 기준 · `report-recovery/1`

운영 중인 DB를 과거 백업으로 덮어쓰지 않는다. 먼저 별도 DB와 비공개 파일 영역에 복원하고, 백업 이후의 계획환율·정정·철회·관리자 권한과 비교한다. 배포 복귀와 데이터 복구는 다른 절차다.

2026-11-03의 [메일 포함 운영 전환표](operating-final-check-20261103.md)를 함께 적용한다. 공개 전 빌드 실패는 현재 사이트를 유지하고, 공개 후 코드 오류는 기능 잠금과 수정/되돌리기 커밋의 CI 재배포로 처리한다. DB 복원에는 최신 발송 여부·미확정 SMTP·비용 장부도 대조하며, 결과가 불명확하면 재발송/재과금하지 않는다.

## 이번에 실행한 범위

- 기존 격리 로컬 DB를 읽기 전용으로 내보냈다. 운영 DB에 연결하지 않았다.
- DB 전체와 DB가 참조하는 로컬 파일, 기존 환율 전체/폴백/원시표, migration 소스를 같은 암호화 묶음에 넣었다. 연결된 파일 12묶음은 합성 시험 자료이며, 별도로 수집한 기사 HTML/PDF와 API 자격증명 파일은 포함하지 않았다.
- AES-256-GCM으로 암호화하고 키는 저장소 바깥의 별도 폴더에 두었다. 백업·키·복원 폴더는 현재 사용자와 SYSTEM으로 접근을 제한했다. 키 값은 문서·브라우저·로그에 표시하지 않는다.
- 같은 로컬 PostgreSQL 서버 안의 새 DB에 복원했다. 기존 서버 역할을 유지해야 하므로 로컬 `supabase_admin` 역할로 복원했다. 원본의 권한을 넓히거나 소유권을 생략해서 오류를 피하지 않았다.
- 복원 직후 테이블 내용 해시, RLS·GRANT·함수 정의와 파일 해시를 비교했다. 파일의 저장 완료 표식은 내용과 이용 범위의 승인을 뜻하지 않는다.
- 별도 시험 DB에서만 이후 계획값 저장, 보고서 철회, 관리자 비활성화를 재현했다. 알려진 철회는 숨기고, 이전 백업과 새 상태가 다르면 전환을 보류한다.

이 결과는 **로컬 복원 검증**이다. 운영 복구 승인, 다른 장비의 복구, 회사 전체 장애 복구 또는 실제 AI 원고 품질 합격으로 확대하지 않는다.

## 삭제 없는 보존 점검

`npm run report:recovery:inspect`는 로컬 파일만 읽는다. Docker·운영 DB·외부 API·키에는 접근하지 않는다.

검사 결과를 다음처럼 읽는다.

| 상태 | 의미와 처리 |
| --- | --- |
| protected | 발행/검토/비용 미확인/진행 중/분쟁/복원 의존 등 보호 사유. 삭제하지 않는다. |
| unverified | 이용 범위 또는 장부 밖 참조가 확인되지 않음. 사용하지 않는 자료라고 추정하지 않는다. |
| incomplete_or_changed | 저장 중단 또는 해시 불일치. 후속 입력·승인에 사용하지 않는다. |
| rights_conflict | 저장 제한과 보존 의무가 충돌함. 재사용을 보류하고 출처 조건에 따른 별도 조치를 검토한다. 무기한 보존도 자동 삭제도 하지 않는다. |
| cleanup_candidate | 제안 기한을 지난 미참조 자료의 예행연습 결과. 실제 삭제 명령이 아니며 실행 직전 참조 재검사가 필요하다. |
| orphan/unverified_external_references | 장부에서 참조되지 않아도 외부 실행·원고·복원본의 참조는 알 수 없음. 자동 삭제하지 않는다. |

같은 파일을 여러 묶음이 사용하면 내용은 한 번만 세고 모든 참조를 남긴다. 논리 합계와 고유 내용 용량을 구분한다. 7/30/90일 등 기간과 경보 수치는 여전히 로컬 예행연습 기준이며 운영 적용·자동 삭제 승인이 아니다.

## 복구 실행 순서

1. **범위 고정:** 대상 DB·버전·출처 이용 조건·파일 참조·기준시각·진행 중 작업·비용 예약을 기록한다. 운영 백업은 별도 승인 범위를 확인한다.
2. **일치하는 묶음 생성:** DB를 일관된 스냅샷으로 내보내고 그 DB가 참조하는 파일을 확인한다. 내보내기 전후 상태가 달라 동일 시점을 입증할 수 없으면 혼합 백업을 완료 처리하지 않는다. 운영의 지속 쓰기에는 공유 스냅샷 또는 검증된 복구 시점/변경 기록 설계가 추가로 필요하다.
3. **암호화·접근 제한:** 백업과 키를 분리하고 허용된 담당자만 접근하게 한다. 원문은 백업 권한까지 확인된 자료만 포함한다. 공개 Git·Netlify·공개 Actions artifact에 올리지 않는다.
4. **새 대상에 복원:** 새 DB와 새 비공개 폴더에만 복원한다. `--clean`이나 기존 데이터 덮어쓰기를 기본 경로로 사용하지 않는다. 데이터 파일은 모든 해시를 먼저 검증하고 완료 표식을 마지막에 쓴다.
5. **정합성·권한 검사:** 값/행/해시·참조·RLS·함수·공개 투영과 익명/비관리자/관리자/service role 경계를 확인한다. DB 백업은 Storage 파일 본문이나 서버 설정·비밀값의 복구를 대신하지 않는다.
6. **최신 상태 재결합:** 백업 이후 저장된 계획환율, 검토/철회/정정, 관리자 권한, 출처 이용 제한·삭제 의무, 진행 중 작업과 비용 예약을 최신 장부와 대조한다. 최신 장부가 없으면 공개/집필/재호출을 보류한다. 새 저장·정정 기록은 append-only로 보존하고 자동 병합하지 않는다.
7. **별도 복구 승인:** 동일한 상태가 됐어도 자동으로 운영에 연결하지 않는다. 관리자 검증 → 제한 조회 → 기존 환율·계획 저장·메일 확인 순으로 전환한다. 실패 시 현재 정상 경로를 유지한다.

`reconcileRecovery`는 계획값·원고 판본/철회·관리자 상태의 비교 도구다. 그 자체가 출처의 최신 이용 허가나 전체 비용/작업 장부의 완전성을 검증하는 도구는 아니다. `latestVerified`는 확인 가능한 최신 입력에만 지정한다. 결과가 `ready_for_separate_promotion_review`여도 운영 전환 승인은 별개이며, 자동 덮어쓰기와 자동 전환은 항상 금지다.

## 정정과 캐시

- 철회된 ID를 알게 된 클라이언트는 이후 장애나 오래된 복원 서버의 응답으로 같은 ID를 정상화하지 않는다.
- 아직 철회를 확인하지 못한 오프라인 기기는 즉시 철회를 알 수 없다. 마지막 확인 시각과 제한된 캐시 기간을 표시하고, 재접속 후 최신 철회를 우선 반영한다. 영구 오프라인 기기에서 즉시 철회를 보장하지 않는다.
- 복원 DB의 과거 공개 상태를 그대로 서비스하면 새 기기에는 철회본이 다시 보일 수 있다. 따라서 최신 철회·권한·출처 상태 재결합 전에는 복원 DB를 공개 경로에 연결하지 않는다.

## 운영 전 미완료 조건

- 실제 운영 데이터의 승인된 백업과 최신 계획환율·비용/실행 장부를 함께 보존하는 방법.
- 다른 장비/별도 클러스터에서 역할·확장·Auth 설정과 파일을 재구축하는 시험.
- 이 PC와 분리된 비공개 보관 위치, 키 담당자·분실 복구·회전·보관 개수. 현재 두 폴더는 같은 물리 장비이므로 장비 손실 대비가 아니다.
- 실제 서비스의 복구 목표 시간/허용 손실 범위와 복구 담당자.
- Storage를 도입하면 파일 본문·허가·삭제 장부의 별도 백업과 복원.
- 복원본의 보존 기한·출처 조건 변경과 의무 삭제를 반영할 운영 절차. 이번 작업은 기존 원문·원고·이력을 실제 삭제하지 않았다.

## 재현 가능한 자료

- 공통 구현: `scripts/currency-report/recovery.js`, `recovery.test.ts`, `recovery-local.js`.
- 이번 실행 기록: `.local-reports/private/recovery-20261030/`의 암호화 백업 수령 기록, 복원 대조, pgTAP, 접근 검사와 보존 검사. 민감 기록은 Git에서 제외한다.
- 암호화 복구본과 키의 실제 위치는 비공개 `backup-receipt.json`에서 확인한다. 키 파일을 브라우저에 붙여 넣거나 공개 링크로 제공하지 않는다.
- 시험으로 만든 DB와 복원 사본은 확인용으로 남겼다. 삭제하려면 해당 이름과 용도를 확인해 별도로 처리한다. 원본 DB에 정리 명령을 실행하지 않는다.
