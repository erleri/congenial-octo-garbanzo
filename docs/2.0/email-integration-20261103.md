# 승인된 환율 리포트의 이메일 연결 — 2026-11-03

## 현재 결과

승인·공개된 리포트를 기존 일일 메일에 넣는 경로와 발송 기록에 따른 중복 방지를 로컬에서 구현·검증했다. 실제 SMTP 발송, 새 AI 호출, 원격 push, Actions 실행, 운영 DB·변수·배포 변경은 하지 않았다.

메일은 기존 앱 진입 버튼 → 새 리포트 → 기존 환율 카드·차트 순서다. 새 리포트가 없으면 리포트 구역을 생략한다. 최대 6개 통화의 제목·승인된 요약·발행 이유를 넣는다. 별도로 승인한 이메일용 요약이 없으면 승인된 요약 전체를 사용하며, 실행 중 AI 요약이나 임의 문장 자르기를 하지 않는다.

`리포트 읽기`는 `/?run=공개판본ID#report/통화/기준일`로 이동한다. 메일에 소개한 판본을 열며, 나중에 같은 날짜가 정정되더라도 예전 링크를 다른 원고로 조용히 바꾸지 않는다. 앱의 정정·철회 상태 조회를 사용한다.

## 자료가 메일이 되는 순서

1. 기존 환율 로더가 준비한 데이터를 읽고 본문·기준일·한국 날짜·자료 해시를 고정한다.
2. 차트도 같은 저장 데이터를 사용한다. 파일이 바뀌거나 차트 해시가 다르면 전송 전에 중단한다.
3. 서버 전용 조회로 마감 시점까지 승인·공개된 최신 리포트를 통화별 최대 한 건 고른다. 초안·미래 승인·시험본·과거 검토본은 제외한다.
4. 수신자별 발송 기록과 비교해 이미 소개한 판본을 제외한다. 과거에 소개한 원고의 정정·철회는 별도 변경 안내로 전달한다.
5. 발송할 제목·본문·링크·차트를 고정하고 공개 상태를 다시 검사한다. 그 사이 철회·변경됐다면 미발송 본문을 환율 전용으로 교체한다. 이전 본문도 기록에 보존한다.
6. 전송 시작을 DB에 기록한 뒤 수신자별 SMTP 요청을 한 번 한다. 결과를 저장하고 불명확한 결과는 자동 재시도하지 않는다.

발행 이유는 저장된 발행 판단 자료를 사용한다. 현재 일간 변동이나 제목을 보고 누적 절상·절하를 추정하지 않는다. 정기 점검과 정정은 해당 기록에 맞춰 표시한다.

## 반복 실행·장애 시 행동

| 상황 | 처리 |
| --- | --- |
| 같은 한국 날짜에 재실행·동시 실행 | 수신자별 같은 발송 건을 사용한다. 수락됐거나 진행 중이면 다시 보내지 않는다. |
| 같은 Actions 실행을 자정 이후 재실행 | 원래 실행 ID에 연결된 날짜·메일을 유지한다. 다음 날 새 메일로 취급하지 않는다. |
| 다음 날 새 실행 | 새 일일 메일은 가능하지만 이미 소개한 리포트를 다시 넣지 않는다. 새 수신자의 소개 이력은 별도로 판단한다. |
| 오래된 날짜의 원고가 정정됨 | 최신 일반 리포트를 밀어내지 않고 기존 독자에게 정정 안내를 보낸다. |
| 리포트 조회만 실패 | 고정된 기존 환율 메일은 보낼 수 있다. 초안으로 대체하지 않는다. |
| 발송 기록 DB에 쓰지 못함 | SMTP 전에 중단한다. 중복 방지 기록 없이 발송하지 않는다. |
| SMTP 수락 후 DB 응답 유실·프로세스 종료 | 전송 중·결과 불명 기록을 유지하며 재발송을 막는다. 운영자가 근거를 확인해 조정한다. |
| SMTP가 특정 주소를 550으로 거절 | 해당 수신자만 보류하고 다른 수신자를 계속 처리한다. 원래 수신자 목록은 지우지 않는다. 재허용은 확인 근거가 필요하다. |
| 로그인·연결 등 전송 전 실패 | 실패를 기록하고 자동 재시도하지 않는다. |

SMTP의 `250 수락`은 전송 서버의 수락이다. 최종 수신함 도착과 다르며, 나중에 도착하는 postmaster 반송 메일의 자동 읽기·수신자 정리는 아직 연결하지 않았다.

## 설정과 운영 전환

기존 운영 설정은 바꾸지 않았다. 로컬 Actions 파일에만 다음 선택 경로를 준비했다.

| 설정 | 동작 |
| --- | --- |
| `FX_EMAIL_REPORT_MODE=legacy` 또는 미설정 | 기존 메일 경로를 유지한다. |
| `FX_EMAIL_REPORT_MODE=shadow` | 기존 메일은 그대로 보내고 새 리포트 조회를 읽기 전용으로 점검한다. 새 발송기에는 SMTP 비밀값을 주지 않는다. |
| `FX_EMAIL_REPORT_MODE=approved`, `FX_EMAIL_SEND_APPROVED=false` | 새 경로를 조회만 하며 메일 발송은 보류한다. 기록 없는 기존 발송기로 우회하지 않는다. |
| `FX_EMAIL_REPORT_MODE=approved`, `FX_EMAIL_SEND_APPROVED=true` | 새 발송 기록 경로만 사용한다. 기존 발송기와 동시에 실행하지 않는다. |
| `FX_EMAIL_HOLD=true` | 메일 발송을 중지한다. 기존 환율 갱신 작업을 유지한다. |

발송 경로 선택은 메일 작성 단계의 출력을 고정해 사용한다. 실행 중 서로 다른 단계가 변경된 변수를 읽어 양쪽 발송기를 실행하는 일을 피한다. 실제 전송 명령은 지정된 GitHub 저장소의 승인된 workflow 환경에서만 허용하며 로컬 CLI는 `--send`를 거절한다.

**무발송 점검은 독립 CLI의 `--plan`을 사용한다.** 전체 Daily workflow를 shadow로 실행하면 기존 메일은 실제 발송된다. shadow를 무발송 모드로 혼동하지 않는다.

운영 전환 때에는 새 migration 적용·서비스 전용 권한 확인·설정 등록을 별도 승인 범위에서 수행한다. 기존 발송기에 이미 발송한 당일 기록을 새 기록으로 추정해서 만들지 않는다. 최초 전환은 다음 새 발송일로 잡거나 실제 발송 여부를 확인해야 한다.

불명확한 발송을 복구할 때 legacy로 바꿔 다시 보내지 않는다. `FX_EMAIL_HOLD=true`로 멈추고 SMTP/발송 기록의 근거를 확인한다. DB 복원 후에도 보류를 유지한 채 백업 이후의 발송 기록을 대조한다. SMTP와 DB를 하나의 트랜잭션으로 묶을 수 없으므로 모든 장애에서 정확히 한 번 도착을 보장한다고 표현하지 않는다.

메일의 본문·차트·발송 이력은 서버 전용 데이터다. 새 7개 테이블을 기존 용량·보존 정책의 운영 점검 대상에 포함하고, 발송 여부가 미확정인 기록은 용량 정리를 이유로 삭제하지 않는다. 이전에 준비한 운영 전환 사본에는 이번 메일 변경이 없으므로 배포 전에 기준 사본을 다시 만들어야 한다.

## 검증 증거

| 검증 | 결과 |
| --- | --- |
| 저장된 실제 승인 원고 6통화 | 기존 원고를 고치지 않고 조회·연결 |
| 일회용 실제 Postgres + 모의 SMTP | 16개 흐름 통과: 중복·동시 실행·자정·정정·철회·장애 포함 |
| pgTAP 권한·상태 검증 | 21개 통과, 트랜잭션 롤백 |
| 실제 격리 PostgREST | 6통화 조회, 중복 차단, 저장 응답 유실 후 중복 차단, 익명 접근 거절 |
| 기존 공개 데이터 | 15개 테이블 행 수·내용 해시 동일 |
| 설정 조합 | legacy/shadow/approved × 발송 승인 × 중지: 12조합 통과 |
| 모의 SMTP 프로토콜 | 5개 통과, 소켓·실제 주소 사용 안 함 |
| 전체 회귀 | 180파일 1,292개 통과, 오류 0 |
| 타입·전체 린트·빌드 | 운영·앱·리포트 빌드 통과, 번들 경계 통과 |
| DB 보안 점검 | 공식 CLI: 경고 이상 문제 없음 |

테스트 수는 원고 품질 표본 수가 아니다. 시간·승인 신원·전송 결과를 합성한 재생과 실제 원고 내용을 구분했으며, 모든 SMTP 전송은 주입한 모의 함수로만 수행했다.

재현 명령은 저장된 11월2일 데이터가 있는 비공개 검증 폴더를 사용한다. 루트의 오래된 환율 파일로 바꿔 검사하지 않는다.

```text
node scripts/email/verify-wiring-local.mjs
node scripts/email/verify-delivery-local.mjs --setup
node scripts/email/verify-delivery-local.mjs --directory <새로 반환된 검증 폴더>
python -m unittest discover -s scripts/email -p test_smtp_transport.py
```

완료한 검증 폴더의 실행 기록은 덮어쓰지 않는다. 상세 증거는 Git에서 제외된 `.local-reports/private/email2-delivery-20261103/`의 `run-W6Nrbv/result.json`, `http-final.json`, `workflow-modes-final.json`, `full-tests-current.json`에 보존했다. 공개 가능한 완료 상태는 [상태 기록](email-integration-status-20261103.json)에 있다.
