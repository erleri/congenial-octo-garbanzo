# 입력 판본·국가별 재개 독립 재점검 — 2026-11-02

## 판정

**유료 전체 재시험으로 바로 넘어가지 않는다. 자동 복구를 막는 공통 결함 두 가지와 실행 결과의 장애 표시 누락이 남아 있다.**

앞선 R1~R3의 수정이 무효라는 뜻은 아니다. 해당 통화 가격 변경의 요청 키 분리, 다른 통화 갱신 후 정상 재개, 저장 완료 응답 유실과 외부 목록 장애의 조합은 기존 검사에서 통과한다. 이번에는 그 검사에 없던 **실패 결과를 반환하는 수집기**, **여러 회차 지속되는 국가별 장애**를 확인했다.

같은 에이전트가 앞선 구현의 가정과 별개로 수행한 재점검이다. 다른 모델·별도 에이전트의 독립 판정이라고 표시하지 않는다. 제품 코드·원고·환율·비용 기록은 수정하지 않았다. 비공개 재현 도구와 점검 문서만 추가했다.

## S1 · 조회 실패를 자료 변경으로 오인해 복구할 작업을 종료 — 높음

- 위치: `scripts/currency-report/operating-cycle.js:95`, `scripts/currency-report/automatic-supply-plan.js:32`, `scripts/currency-report/selected-source-collection.js:247`.
- 경로: 집필 완료·검토 대기 → 무료 수집이 빈 기사 목록과 `access_failed` / `extraction_failed` / `discovery_incomplete` 결과를 반환 → 다음 회차에 원래 기사가 다시 조회됨.
- 원인: 재개 경로는 `acquisitionError`가 있는 경우만 조회 실패로 본다. 실제 수집기는 예외 대신 결과의 `outcomes`에 실패를 담기도 한다. 이때 빈 목록의 해시를 옛 기사 목록과 비교해 `frozen_country_material_superseded`로 사건을 종료한다.
- 관찰: 복구된 자료가 원래 입력과 같으면 완료된 배치의 결과를 반환한다. 해당 원고의 검토는 재개되지 않고 합성 초안은 5개에 머문다. 같은 입력으로 반복 실행해도 같다. 새로운 가격/자료가 생긴 뒤의 별도 사건 가능성과 구분한다.
- 범위: **6통화 × 실패 결과 3종 = 18조합 모두 재현**. COP 한 사례는 실제 저장 어댑터와 설치된 격리 DB 함수로도 재현했다.
- 중복 모델 전송은 없고 옛 응답·비용은 보존된다. 문제는 안전한 중복 방지가 잘못 종료한 작업의 정상 복구까지 막는 데 있다.
- 수정 방향: 수집의 완전성/조회 실패와 자료의 새 판본을 별도 상태로 판단한다. 관측하지 못했다는 사실을 원문의 변경·철회 증거로 사용하지 않는다. 실패를 반환하든 예외를 던지든 같은 복구 규칙을 적용한다. 이미 잘못 종료된 사건은 원래 응답·장부를 보존한 명시적 복구 대상으로 식별한다. 정상 내용 반려까지 무조건 재개시키면 안 된다.

## S2 · 한 국가의 지속 장애가 다른 국가의 새 입력을 계속 막음 — 높음

- 위치: `scripts/currency-report/operating-cycle.js:68`, `scripts/currency-report/operating-cycle.js:86`, `scripts/currency-report/operating-cycle.js:168`.
- 경로: COP·PEN 원고 검토 대기 → COP 기준환율 갱신 → PEN 무료 수집만 계속 실패 → 세 번의 후속 예정 실행.
- 관찰: COP의 옛 사건은 올바르게 종료되지만 PEN이 대기 중이므로 전체 배치가 계속 `paused`다. 다음 실행도 그 배치의 옛 입력만 선택한다. COP 새 입력은 수집되어도 실행되지 않는다. COP 상태는 이후 `unchanged_case_already_processed`로 바뀌며 합성 초안은 4개에 머문다.
- 실제 저장 어댑터/격리 DB에서도 동일하게 재현했다. PEN이 복구돼 원래 배치가 마무리되면 COP의 다음 입력을 시작할 수 있지만, **PEN 장애가 지속되는 동안 COP가 종속되는 것**이 결함이다.
- 기존 회귀는 두 국가가 대기하다가 다른 한 국가가 바로 복구되는 경우였다. 그 조건에서의 성공만으로 장기 장애 격리를 확인할 수 없다.
- 수정 방향: 통화별 대기 작업과 새 작업의 실행 기회를 배치의 전체 완료 여부에서 분리한다. 원래 작업·비용·승인 소유 관계를 유지하며 통화별 후속 작업을 선택할 수 있어야 한다. 전역 비용 미확인·예산·권한 장애는 계속 전체를 중단한다. 임의로 새 배치 ID를 만들어 예약 한도나 일회 승인 범위를 우회하는 방식은 쓰지 않는다.

## S3 · 현재 수집 장애가 실행 반환값에서 빠짐 — 중간

- 위치: `scripts/currency-report/operating-cycle.js:170`, `scripts/currency-report/operating-result.js:5`.
- 원인: 준비 결과에는 `collectionResults`가 있지만 실제 실행 후 반환에는 포함되지 않는다. 결과 분류기는 이 필드의 `lookupFailures`로 전체/부분 수집 실패를 판별한다.
- 관찰: S1의 실패 회차와 S2의 지속 실패 회차에서 최상위 분류는 `review_wait`, 종료 코드 0, `partialSourceFailure:false`였다. 다른 통화의 정상 초안이 있어도 현재 수집 장애가 사라지면 안 된다.
- 제한: 개별 공급 상태는 별도 `supplyCheck`에 기록될 수 있다. 모든 관리자 기록에서 실패가 삭제된다는 주장은 아니다. **실행 요약·종료 코드 경로의 누락**이다.
- 수정 방향: 현재 수집 결과와 동결 입력의 처리 결과를 구분해 모든 반환/저장 분기에 전달한다. 정상적인 내용 보류, 대체 자료로 계속할 수 있는 부분 장애, 기술적 복구 실패를 각각 표시한다. 출처 하나의 일시 실패만으로 모든 국가를 강제 중단하는 규칙을 만들지는 않는다.
