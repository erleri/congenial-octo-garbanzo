## 4. 설정·실행·공개의 중지 계약

아래는 목표 계약이며 현재 운영 구현 완료가 아니다. 현재 `FX_REPORT_ENABLED`가 생성된 TS 파일을 거쳐 UI에 적용되는 경로는 새 배포가 필요하다. 생성된 파일만 수동으로 false로 바꿔도 다음 정기 작업이 repository 변수에 따라 다시 쓸 수 있다. GitHub 변수 변경 하나로 기존 브라우저와 실행 중 요청까지 즉시 중지된다고 보고하지 않는다. 새 Sol 선택은 공통 `writer-policy`의 명시 프로필을 따르며 legacy의 `FX_REPORT_AI_MODEL` 기본 무료 모델 설정과 혼합하지 않는다. 이번에는 최신 제공 경로/가격을 재확인하거나 모델을 호출하지 않았다.

## 5. 배포와 복구 체크포인트

1. **설계도 합의:** 앱 전체와 리포트 상세 흐름을 사용자와 확인한다. 여기서 실제 UI 기능/메뉴 변경을 먼저 결정한다.
2. **리포트·UI 구현 마감:** 6통화 자료 상태·집필/검토/승인, 운영 provider·저장·중지 경로를 확인한다. 유료 시험은 필요한 경우 그때 예산 승인한다.
3. **분리 PR 준비:** 그때 최신 main을 다시 확인해 P1~P6을 필요한 단위로 구성한다. 운영 데이터 파일은 최신 main을 보존하며 계정/키/수신자/원문/비공개 실행 기록을 포함하지 않는다.
4. **검증용 배포:** 별도 승인된 프리뷰/테스트 DB를 사용한다. 운영 service role·운영 DB/메일/모델 자동 실행을 연결하지 않는다. 실제 공개 기사·원문 파일을 프리뷰 정적 파일로 올리지 않는다.
5. **운영 DB/코드 승인:** 실제 운영 백업과 독립 복구·최신 변경 보존 확인 후 DB 구조 추가 → 호환 코드 비활성 배포. 이미 저장된 계획환율이 그대로인지 비교한다.
6. **관리자 파일럿:** 기존 1.x를 유지하며 최소10영업일/평가 가능한 초안10건 등 합의한 기준으로 평가한다. 20영업일에도 부족하면 표본 부족으로 보고하며 강제 발행/합격 처리하지 않는다.
7. **2.0 공개 승인:** 사용자 확인과 파일럿 합격 후 범위·모델·예산·담당자·중지/복구 절차를 확인해 제한 공개한다. 자동 게시·이메일 보강은 별도 승인이다.

| 문제가 생긴 범위 | 먼저 할 일 | 복귀할 때 보존할 것 |
| --- | --- | --- |
| 새 리포트 조사/AI | 새 경로 중지, 기존 FX/메일 유지 | 실행 ID·미확인 비용 예약·실패 원문·근거 판본 |
| 공개 원고 | 해당 원고 철회·정정, 최신 상태를 읽기 경로에 우선 반영 | 과거 원고/승인/철회 감사 기록. 캐시로 재공개하지 않음 |
| 화면/새 코드 | 필요한 변경을 revert한 검증된 새 배포, 또는 확인된 이전 정상 경로 | 추가 DB 구조는 남겨 호환. 단순 페이지 복귀로 DB가 복구됐다고 하지 않음 |
| FX/계획/메일 | 새 기능 중지로 회복되는지 확인, 그렇지 않으면 기존 기준 동작으로 복귀 | 최신 환율 생성/동기화 경로와 이후 계획 저장·감사 이력 |
| DB/파일 손상 | 별도 DB/비공개 영역 복원, 최신 상태/권한/출처/비용 장부 재결합 후 승인 | 현재 DB를 과거본으로 덮어쓰지 않음. 삭제한 테이블/공개 권한 복원으로 우회하지 않음 |

## 6. 앞으로 실제 실행할 검증 — 이번에는 계획만 정리

| 경우 | 기대 결과 |
| --- | --- |
| 새 기능 비활성 배포 | 기존 화면/계획 저장/정기 갱신/메일 정상, 새 유료 호출0 |
| 프리뷰가 운영 주소/서버 비밀값을 받음 | 실행 중단. 테스트 DB로 재설정하기 전까지 시험하지 않음 |
| 누적2%와 정기 점검이 같은 사건에 겹침 | 같은 원고 한 건으로 묶고 이미 대기/실패/보류된 이력과 비교 |
| 자료 없음/뉴스 조회 실패/오래된 소비 지표 | 서로 다른 상태로 기록. 월간 지표를 당일 원인으로 만들거나 발행을 강제하지 않음 |
| legacy와새 경로가 같은 입력을 받음 | 단일 소유 경로/영속 중복 키가 허용한 실행 하나만 집필 |
| 모델 시간 초과·비용 미확인 | 비용 예약 보존, 자동 재시도/백업 모델 없음, 기존 메일 정상 |
| 저장 후 실행 환경 소멸 | 승인에 필요한 비공개 파일과 영속 참조가 남음. 없으면 승인 차단 |
| 비관리자·권한 해제·동시 승인 | 비공개 자료 차단, 한 승인만 원자적으로 반영 |
| 철회 후 DB 장애·오래된 캐시 | 알려진 철회 ID 재노출 없음. 오프라인 미확인 상태는 시각/유효기간 표시 |
| 운영으로 넘어가기 전 새 계획값 저장 | 이후 저장·이력을 과거 백업으로 덮어쓰지 않음 |
| 새 UI 기능·탭 이동 | 사용자에게 승인받은 FigJam 구조와 URL/뒤로가기/모바일/인쇄 동작 일치 |

위 표를 이번에 새로 실행했다고 보고하지 않는다. 이전 1~5단계의 1,039개 자동 사례와 로컬 복원/74개 pgTAP 결과는 해당 시점·해당 코드에서의 근거이며 미래 분리 PR/프리뷰/새 AI 품질을 대신하지 않는다.

## 7. 책임과 승인 경계

- 코드 정리·검증·변경 설명: Codex. 운영 승인과 공개 범위 결정: 사용자.
- 백업 독립 보관 위치·키 책임/분실 복구·복구 시간/손실 목표·월 예산: 운영 활성화 전에 사용자와 확정. 이번에 임의 수치로 확정하지 않는다.
- 원고 최종 승인 담당자: active admin 중 사용자가 지정. 담당자가 없으면 대기하며 자동 게시하지 않는다.
- 기존 메일 수신 확인: 승인된 검증 발송 후 사용자 확인. 이번에는 발송하지 않는다.
- 다른 대화에 메시지를 보내거나 그 설계도를 변경하지 않았다. 기존 초안은 다음 단계에서 재사용한다.
